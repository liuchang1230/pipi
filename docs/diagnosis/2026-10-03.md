## 远程 tab 启动即死：旧手写委派目录与新 delegation 抢工具名，而横幅只显示了 pi 的劝告 (2026-10-03)

**症状（用户报告）**：远程服务器上的会话 tab 起来就死，只看到一行

```
Pi 进程异常退出（code 1） · Hint: Start without extensions using "pi -ne".
```

即我们自己的崩溃横幅 + pi 的劝告。用户拿到的**唯一信息是一句"用 `pi -ne` 启动"**——对一个起不来的机器说
"你换个方式启动"，没有任何可行动的内容。

### 回路（Phase 1）：用真 pi 把这条故障变成红的

这个 bug 的优点是不需要跑 app：pi 的启动失败是纯配置后果，`PI_CODING_AGENT_DIR`（pi 在 `dist/config.js` 里读）
就能把"机器状态"搬进一个临时目录。回路 = **给 pi 一个 agent dir，看它 exit code 与 stderr**。

```bash
# 对照：只有 app 现在投递的 delegation/
PI_CODING_AGENT_DIR=$REPRO/good  pi --mode rpc < /dev/null   # exit=0，stderr 空
# 复现：再加一个注册同名工具的旧目录
PI_CODING_AGENT_DIR=$REPRO/bad   pi --mode rpc < /dev/null   # exit=1
```

红的输出逐字复现用户症状（路径为本机临时目录）：

```
Error: Failed to load extension ".../bad/extensions/delegation/index.ts": Tool "analyst" conflicts with .../bad/extensions/analyst/index.ts
Hint: Start without extensions using "pi -ne".
```

**最小化**：把 `delegation/` 那 1,187 行换成两边各 10 行的桩，仍然 exit 1；删掉任一边就 exit 0：

```
both-register-analyst exit=1
Error: Failed to load extension ".../min/extensions/b/index.ts": Tool "analyst" conflicts with .../min/extensions/a/index.ts
Hint: Start without extensions using "pi -ne".
single exit=0
```

→ **每项都承重，且承重的只有一件事：两个目录扩展注册了同一个工具名。** 引擎、声明、渲染全都无关。
pi 在 `main.js` 里 `hasRuntimeErrors` 之后就 `process.exit(1)`，所以重名注册不是警告，是**启动即死**。

### 根因

远程 `/home/crscu/.pi/agent/extensions/` 里**新旧委派层并存**：

| 目录 | 来源 | 注册的工具 |
|---|---|---|
| `delegation/index.ts` | app 现在投递（2026-09-30 收编） | analyst / reviewer / scout |
| `analyst/` `reviewer/` `scout/` | 收编**之前手写**的旧版 | 同样三个名字 |

### 为什么没有任何代码路径能清掉它

两条退役路径**都只认「我们投递过的文件」**：

- journal 路径（`content-sync.ts` 的 `planSync`）：只退役出现在 `journal.shipped` 里的 relPath。
- pre-journal 路径（`extension-sync.ts` 的 `RETIRED_FILES`）：靠 sha256 或 markers 认**我们投递过的字节**，
  而且**粒度是单文件，结构上就没有"退役一个目录"这回事**。

而 git 全史证明 `src/main/extensions/` 下**从来没有过** `analyst/ reviewer/ scout/`：

```bash
git log --all --pretty=format: --name-only --diff-filter=A -- src/main/extensions/ | sort -u
# → 只有 delegation/{index,agents,declarations,engine,render}.ts、pipi-*.ts、pi-api-stub.d.ts
git log --all -- src/main/extensions/analyst/    # 空
```

它们是在 `~/.pi/agent/extensions/` 里**手写**的（2026-09-30 文档自己写着「这个目录没有版本控制」）。
9-30 收编成 `delegation/` 时，旧目录是**在本地手工删掉**的（文档：「备份是唯一回滚手段」）——
**「从机器上删掉旧拷贝」这一步从来没进过代码**，所以远程的服务器没跟上。

结论：**任何曾经手装过那三个目录的机器（本机以外，即所有远程/WSL），冲突都会永久保留。**

### 顺带查出的第二个 bug：横幅把唯一的原因吞掉了

完整 stderr 里 pi 打了 3 条 `Error:`，**最后**才是那条劝告。而 `pickExitErrorLine` 的规则是
「取最后一条非噪声行」→ 命中劝告 → `exitBannerText` 的 detail 只有 `Hint: Start without extensions...`。
**从 pi 的"诊断 + 劝告"结构看，这个启发式必然取到劝告，永远取不到原因。**
（完整 stderr 一直躺在 `pipi-debug.log` 的 `EXIT` 行里，只是 UI 拿不到——见下面的"尚未做"。）

修法（`src/renderer/src/stores/chatStore.ts:23-40`）：把 pi 的收尾劝告与 bash job-control 噪声同等对待
（都不是原因），并让**以 `Error: ` 开头的 pi 诊断行优先于"最后一行"启发式**；
`Error: ` 必须带空格，否则会误伤 `TypeError:`。

回归测试用**用户报障时贴出的真实 stderr 逐字**断言，含那条误导性的 `pi-web-access` 警告
（`__tests__/chatStore.test.ts:540-563`）：`pipi` 的横幅必须说出 `Tool "analyst" conflicts`，
不得是 `pi -ne`，也不得是扩展的版本警告。

### 排除掉的两条（记下来免得下次重查）

- `[pi-web-access] Dynamic tool activation requires Pi 0.86.0 or newer; web tools remain eagerly available.`
  —— **警告**，扩展继续可用，不导致 exit 1（它在 `EXIT -1` 的连接断开行里也出现）。只说明远程的 pi < 0.86.0。
- 那批 `EXIT -1` 的「SSH 连接已断开」是传输层掉线，已由既有 `CONNECTION_LOSS` 分类正确覆盖，与本次无关。

### 处置

- **服务器侧（用户手工，无版本控制故先备份）**：看清内容后把三个旧目录移走，重开 tab。
  ```bash

  mkdir -p ~/extensions-backup-$(date +%Y%m%d) && mv analyst reviewer scout ~/extensions-backup-$(date +%Y%m%d)/
  ```
  若里面有自己的改动：`delegation/declarations.ts` 已覆盖同样能力，把改动并进去。
- **本仓库**：横幅修复 + 回归测试（68/68，`tsc -p tsconfig.web.json` 通过）。

### 教训

1. **「取最后一行」这种启发式，在「诊断在前、劝告在后」的输出上必然取到劝告。** 有用行不是"最后一行"，
   而是"**带错误前缀的那一行**"。凡是解析别人的 stderr，先认它的前缀约定（pi 是 `Error: `），
   再谈位置。代价：用户看到的是"换个方式启动"，而真相（哪个工具跟哪个文件冲突）已经躺在日志里了。
2. **退役机制只认识自己投递过的字节 —— 手写产物不在其中，而收编恰恰会把它们变成硬冲突。**
   把三份手写扩展收成一个 app 投递的 `delegation/` 时，**"删掉旧拷贝"是收编的一半工作量**。
   只做本地手删 = 只修了一台机器。
3. **本次没做，留档**：这三条目前只能靠人读横幅去修（横幅现在说清了）。若要根治，
   需要"启动/连接时检测 `extensions/{analyst,reviewer,scout}/index.ts` 与 `delegation` 抢名并按硬规则 #8 报失败"
   （带精确路径 + 可复制的修复命令，**不静默删**——手写内容是用户的）；或让 `RETIRED_FILES` 支持目录级退役，
   但识别条件要严于文件名。另一个缺口：`exitDetail` 只留一行，完整 stderr 在 UI 上不可复制，
   与稳定性契约 #8 的「可复制证据」不符。
