## 真·硬崩溃：pi SDK 的剪贴板原生插件 (2026-09-28)

用户报告「窗口容易闪退」的其中一半是真崩溃（应用进程整个消失），另一半是弹窗自己关（见下一节）。

**证据（Windows 事件日志 / WER）**：两条 `electron.exe` 36.9.5.0 崩溃记录，`出错模块名称：
clipboard.win32-x64-msvc.node_unloaded`，`异常代码：0xc0000005`（BEX64 类型 5），故障模块路径指向
`node_modules/@earendil-works/pi-coding-agent/node_modules/@mariozechner/clipboard-win32-x64-msvc/clipboard.win32-x64-msvc.node`。
两次崩溃实例都活了 18–24 小时，且都跑过 SDK worker（`[mem] sdk-worker-start` 只出现过两次，正好对上
两次崩溃前的启动）；其中一次崩溃时进程处于 **idle**（崩溃前只有 `[mem] tick`）。崩溃后 32 秒出现新的
`[mem] startup` —— 主进程真的没了。

**链路**：`@earendil-works/pi-coding-agent/dist/utils/clipboard-native.js` 在**模块作用域**调用
`loadClipboardNative()` → `require("@mariozechner/clipboard")` → NAPI-RS loader 立即
`module.exports = nativeBinding` → DLL 被加载进宿主进程。我们唯一的 import 点就是
`src/main/chat-backend/sdk-worker.ts`（worker_thread，**同一个进程**），所以 Rust 原生插件的崩溃面被
搬进了 electron.exe 主进程。WER 报的是 `_unloaded`，第二个潜在触发点是 `worker.terminate()`
（`closeAllSdkSessions()`，`window-all-closed`/`before-quit`）——卸载期间执行析构。

**修法（不分叉）**：pi 自己提供了开关 —— `clipboard-native.js` 只在模块求值时读一次
`process.env.TERMUX_VERSION`，为真则保持 `clipboard = null`。所以我们**只在动态 import 期间**设置
`TERMUX_VERSION = "pipi-sdk-worker"`，import 完成后立刻恢复（原本是 undefined 就 `delete`）：

```ts
const prevTermuxVersion = process.env.TERMUX_VERSION;
process.env.TERMUX_VERSION = "pipi-sdk-worker";
const sdk = await import("@earendil-works/pi-coding-agent");
if (prevTermuxVersion === undefined) delete process.env.TERMUX_VERSION;
else process.env.TERMUX_VERSION = prevTermuxVersion;
```

**验证（临时 Electron harness，用完即删）**：裸 import → `CLIPBOARD_MODULES=["…@mariozechner/clipboard/index.js","…clipboard.win32-x64-msvc.node","…package.json"]`、
`SDK_LOADED=325`；同一 harness 在 import 期间设 `TERMUX_VERSION` → `CLIPBOARD_MODULES=[]`、`SDK_LOADED=322`
（少了 3 个模块，SDK 其余功能照常）。类型检查 + `sdk-host` 测试通过。

**为什么不全局设这个变量**：环境变量会被 agent 自己的 bash/子进程继承，等于对所有工具撒谎。
**为什么行为安全**：`readClipboardImage/readClipboardText/copyToClipboard` 只被
`interactive-mode.js` / `tui-renderer.js`（TUI）使用，SDK worker 是 headless 的；真正的 TUI 粘贴走
独立进程（pty 里的 pi），不受影响；Windows 上的文本复制另有 `clip` 回落路径。

**教训**：在一个进程里加载第三方 NAPI 插件 = 把它的崩溃面搬进主进程；"只在导入期改环境变量"是零分叉的
开关写法，但必须**立刻恢复**，否则污染会传给所有子进程。


## 「模型配置弹窗自己关掉」= 遮罩 `onClick` 的两端手势 (2026-09-28)

用户原话：「我在编辑模型配置的时候，窗口容易闪退」，澄清后是**只有「模型配置」弹窗自己关掉**，
应用还活着（不是崩溃、不是卡死）。这条排除了上面那个 DLL，也排除了 JS 异常（日志里没有任何相关报错）。

**真因**：`ModelConfigDialog` 的遮罩是 `<div className="dialog-overlay" onClick={onClose}>`。
一次 click 的 `target` 是 **mousedown 与 mouseup 的最近公共祖先**：在输入框里按下（开始选文字）、把鼠标
拖到弹窗外再松开 → click 落在**遮罩**上 → `onClose()` 在编辑过程中触发。弹窗宽 560px 而窗口很宽，
"松手落在遮罩上"随手就能发生。同一写法在仓库里有 11 处。

**修法**：新的 `src/renderer/src/components/overlay-dismiss.ts`
- 纯状态机 `BackdropGesture`：**按下与松开都必须落在遮罩本身**才关闭（Drag-out 永远无法关闭弹窗）；
- `useOverlayDismiss(onDismiss)` 返回 `{onMouseDown, onMouseUp}`，用 ref 保存状态（arm 不触发重渲染）
  与最新回调（调用方传内联箭头也不会让 handler 失效）；
- 用 `mouseup` 而不是 `click` 的第二个理由：原生 `<select>` 选完一项会**合成**一次 click（没有真实按下），
  若用"mousedown gate 的 click"就会在选完模型渠道的瞬间把弹窗关掉。

**全部 11 处**：`ModelConfigDialog`、`FailureCenter`、`PiInstallDialog`（安装中禁止遮罩关闭）、
`RemoteDialog`（顺带清 `remoteStatus`）、`RemoteDirPicker`、`RemotePasswordDialog`、`TreeDialog`、
`UiDialog`、`FileDialogs` 的 `PromptDialog`/`ConfirmDialog`、`SidebarPane` 的重命名弹窗。
`OnboardingDialog` / `QuestionnaireDialog` 本来就不允许点遮罩关闭，不动。

**顺带**：`App.tsx` 里 `ModelConfigDialog` **挂载了两次**（`showModelConfig` 与
`uiStore.appDialog === "model-config"` 各一次），两者同时为真时会有两个实例（两份 `model:list`、两套订阅）。
现在合成一个 mount + 一个 close handler（清 `showModelConfig` 并 `closeAppDialog()`）。

**测试**：`components/__tests__/overlay-dismiss.test.ts` 只测纯状态机 —— 渲染器测试跑在 node 环境
（无 jsdom/@testing-library），DOM 事件测不了，这条规则只能这样固化成契约。

**教训**：遮罩关闭要判"开始与结束都在遮罩上"，`onClick` 判不了；能用 `mouseup` 就别用 `click`。

## 分支树二改：标记列 + 选择态 + 手工会话文件的 version 字段 (2026-09-28)

上一条（同日的「删掉导图视图」）落地后又做了三处修正，另有一条**做种子数据时踩到的 pi 行为**，都值得记下来。

### 1. 「肘线」画不出来 → 改成固定宽度的标记列

**现象**：分支树在一份真的分叉过的会话里，一个 `├`/`└` 都不画（测量：所有 rail 元素都是「关」的）。

**根因**：老方案把肘线画在 `level === connectorPosition`，也就是**父节点所在列**。这套几何**只在「子列 = 父列 + 1」时成立** —— 那是 `indent` 还代表「分叉嵌套深度」的时代（所以需要「折叠单子节点链」的启发式）。改成对话层级后，子节点与父节点**常常同列**，于是肘线要落的那个格子根本不存在，被静默丢掉。

**修法**：把标记放进**每行都有的固定宽度列**（`.tree-marker`，12px），它不依赖父节点在哪一列，因此不可能冲突；缩进退化为纯占位（`.tree-rails` + 每级一个 14px 的 `.tree-rail`）。语义由 `flattenTree` 算出的 `TreeRowMarker` 给出：`branch-mid` ├ / `branch-last` └（本行是多个同级之一）、`continuation` │（上方有未闭合的分支）、`none`。`rootOffset`/`multipleRoots`（多根时的虚拟根列）随之删除。

**两个已知的、接受的取舍**（写在 `tree-layout.ts` 里）：标记是按**完整树**算的，弹窗之后再过滤/折叠，所以被隐藏的同级可能留下一个孤立的 `├`；单标记列只能画**最内层**的开放分支，嵌套的同级组会画成 `├├└└` 而没有外层 `│`。

### 2. 「点了节点没反应」= CSS `background` 简写重置了选择态

**现象**：点一行，DOM 里 `data-selected` 变了、class 也变了，但看不出任何区别。

**根因**：`.tree-row.on-active-path { background: linear-gradient(...) }` 用了 **`background` 简写**，会把 `.selected` 已经设好的 `background-color` 一并重置为透明；而活动路径上的行**几乎都是** `.on-active-path`（弹窗默认滚到叶子，挂载的都是路径上的行），所以选择色永远被覆盖掉。

**修法**：颜色与条纹拆成两个属性 —— `:hover`/`.selected` 只用 `background-color`，`.on-active-path` 只用 `background-image`，两者叠加。**教训：行状态样式永远不要用 `background` 简写**，它是一次重设，不是一次叠加。

同时把探针改成**同一行的 A/B**（选中 → 记录 computed style → 摘掉 `.selected` 类 → 再记录 → 恢复）：原来拿「相邻的另一个行」对比，而挂载窗口里可能**每个行都在活动路径上**（叶子附近就是这样），邻居参照根本不存在，检查会假通过或假失败。现在断言的是「点击后这一行自身的 paint 必须变化」。

### 3. 手工写会话 JSONL 必须带 `version`，否则 pi 会把它拉直

**现象**：诊断脚本种了一份**有两处分叉**的会话（1215 条），APP 里行文都对、分叉全没了 —— 所有行都是 `none`/`continuation`，一个分叉标记都没有。一开始怀疑是打包产物过旧，但 asar 里 `MARKER_GLYPH`/`data-marker`/`isBranchChild` 都在，纯函数管线跑临时测试也完全正确。

**根因**：种子的 header 写的是 `{type:"session", id:"s0", cwd, timestamp}`，**没有 `version`**。pi 的 `SessionManager` 把「没有 version」当成 v1，跑 `migrateV1ToV2`：给每个条目**重新分配 id**、并且 `entry.parentId = prevId` **把每个条目挂到前一个条目上** —— 也就是**把整棵树拉直成一条链**。（`node_modules/@earendil-works/pi-coding-agent/dist/core/session-manager.js:11` 是 `CURRENT_SESSION_VERSION = 3`；`:29-45` 就是那个迁移。）

**修法**：种子 header 写 `version: 3`。**教训**：这个 app 的树有两个来源（pi 的实时 `get_entries` 与 `tree-from-file` 读的原始文件），**手写的会话文件一旦被 pi 当旧格式迁移，两边内容就会不一致**；凡是「种一份带分叉的会话给 UI 断言」的地方，header 必须带 `version`。诊断脚本里现在把这句话写在种子的注释里，并且失败信息直接点名「行是一条链 = 种子被当 v1 迁移了」。

### 4. 复查后的加固（同日晚）

- **`createOverlayHandlers`**：hook 的主体抽成纯工厂，于是「接线」本身可单测（键集恰好三个、按下+抬起只触发一次、按在弹窗里不触发、回调取的是**事件发生时**的最新值）。返回类型用 `Record<keyof Pick<React.HTMLAttributes<HTMLDivElement>, …>, …>`：**键名来自 React 自己的 props**（JSX 展开不做多余属性检查，`onMouseleave` 这种拼写错误以前能编译通过，会在 11 个弹窗上一起静默失效），事件类型仍是本模块自己的 `MouseEventLike`（纯模块不需要 DOM 事件类型）。

## 折叠只折叠下面一条：隐藏集必须沿 parentId 链走，而且要在「未过滤」的列表上走 (2026-09-28)

**症状**：分支窗口里点某一行的 ⊟，只有紧挨着它下面的一条消失，再往下的子孙都还在。

**根因**（这次的坑很典型）：折叠的隐藏集原来是**单趟从左到右**扫「已过滤」的可见列表：

```js
for (const f of visible) {
  const { id, parentId } = f.node.entry;
  if (parentId != null && (folded.has(parentId) || skip.has(parentId))) skip.add(id);  // ← 只看直接父亲
}
```

这个写法依赖两件事同时成立，而它们在真实会话里都不成立：

1. **每个节点的直接父亲都在名单里**。默认过滤（`applyVisibility`）会丢掉 `session_info`/`label`/`model_change` 这类记账行，也会丢掉**只带 toolCall、没有文本的 assistant 行**。于是 `toolResult` 的 parentId 指向一个被过滤掉的行 —— `folded.has(parentId)` 和 `skip.has(parentId)` 全是 false，传播链在这里断掉，它以及它后面的一切都不再被隐藏。只有「父亲正好就是被折叠节点本身」的那一条会消失。
2. **列表是父在前、子在后**。这条其实一直成立（`flattenTree` 是前序），但正因为只有第 1 条是真正的病根，才让「链式种子」上永远测不出来。

**修法**：抽出纯函数 `foldedAwayIds(rows, folded)`（`src/shared/tree-view.ts`），语义明确为「**传完整扁平列表**（`flat`，不是过滤后的 `visible`）」，实现是**沿 parentId 往上走 + 记忆化**：`hidden(node) ⟺ 某个父节点被折叠，或某个父节点被隐藏`，每条链只解一次，整体 O(n)。调用点：

```js
const hidden = foldedAwayIds(flat, folded);          // flat = 完整列表
return hidden.size === 0 ? visible : visible.filter((f) => !hidden.has(f.node.entry.id));
```

两点额外设计：**任何一行都不会被自己的折叠隐藏**（否则折叠后那条行自己也没了，⊞ 就没地方点，展开不回来）——所以 parentId 成环时走到起点即停，环只保证「能终止」；**与顺序无关**，不依赖父在前子在后。

**证据**（都是打包产物上实测）：
- 复现：带分叉的种子（`asks` 下面挂三条分支 + 300 轮尾巴）折叠根行 → 只隐藏 **1** 行（原来只有直接子行消失）。
- 修复后同一个探针：`{"before":913,"after":1,"hidden":912,"glyph":"⊞","restored":913}` —— 折叠根行隐藏 912/913 行，展开后精确恢复。
- 永久回归：`scripts/diagnose-tree-rows.mjs` 新增 fold 探针（折叠头行 → 隐藏数必须 ≥ 10、字形必须变 ⊞、展开必须精确还原）；`scripts/robustness-smoke.mjs` 新增 3 条 check（`SMOKE PASS 40/40`，折叠 `{m0, 9→1, hidden 8, restored 9}`）。
- 单测：`src/shared/__tests__/tree-view.test.ts` 新增 `describe("foldedAwayIds")` 6 条 —— 直接父亲被过滤掉时子孙仍要折叠（就是这次的 bug）、折叠行自己与祖先不被隐藏、**打乱顺序结果不变**、嵌套折叠、未折叠时返回空集、parentId 成环时必须终止且不隐藏折叠行本身。全套 **68 文件 / 812 用例**通过。

**顺带修掉的种子 bug**：`robustness-smoke.mjs` 的种子把会话头写成 `id: "s0"`，而消息 id 也从 `s0` 开始 → 两个条目同 id，`buildTreeFromEntries` 的 `nodeMap` 互相覆盖（折叠探针一度报 `data-row-id: "s0"`）。消息 id 前缀改成 `m`。

**教训**：**「隐藏一行」这种祖先判定，永远不要写成「看直接父亲」的单趟扫描** —— 渲染列表是带洞的（过滤、虚拟窗口、折叠都是洞），必须按 id 沿链解析，或者干脆在完整结构上算。同理，纯函数要把它依赖的前提（这里是「传完整列表」）写进 docstring：调用点传错列表时，代码不会报错，只会静静地少隐藏几行。

### 附：评审揪出的「过度隐藏」（同日）

第一版修的隐藏集是「在**完整** `flat` 上沿链走」，这就多出一条新语义：**被折叠的行自己已经被筛掉了，它的子孙照样被隐藏**。后果很实际 —— 折叠一条回答 → 切到「用户」筛选或搜一个只匹配下层提问的词 → 匹配行也一起消失，界面显示「（无匹配）」，而屏幕上根本没有那个 ⊟ 可以点开（只剩 `展开全部` 这个全局按钮）。

修法：新增 `activeFolds(renderedRows, folded)`（`src/shared/tree-view.ts`）—— **只保留「自己那一行当前被渲染」的折叠**，折叠状态本身仍然保留（`filtered` 只借它算隐藏集，清除筛选后折叠原样回来）。TreeDialog 的「展开全部(N)」和页脚「有折叠」也改成读 `activeFolds`，这样折叠行被筛掉时不会出现「一个看不见的折叠」这种说法。这样两个语义各就各位：

- **隐藏集**要在**完整**列表上算（洞不能断链）—— 修的是「只折叠一条」；
- **生效的折叠**必须是**可见**的行（看不见的 ⊟ 不该藏东西）—— 修的是过度隐藏。

评审同时确认了几件事没问题：`flat` 本身没有洞（每条记录要么是子节点要么是根，`buildTreeFromEntries` 保证了这一点）、`memo` 是函数内的不会泄漏、复杂度 O(n)、环形只保证能终止、任何一行不会被自己的折叠隐藏。另有一条**故意钉住旧行为的测试**（`under-hides when handed a list with the parent filtered away`）：如果有人把调用点改回传 `visible`，这条会失败，指名道姓地告诉他「传可见列表就是那个 bug」。

证据：`npm run smoke:tree` 新增 `fold + search` 探针 —— 折叠头行后再搜「尾部问题 5」：`{"folded":1,"matched":35,"empty":false,"chip":[],"restored":913}`（匹配行照常显示、没有假的「（无匹配）」、`展开全部` 不再出现）。单测 **68 文件 / 816 用例**通过；`SMOKE PASS 40/40`。（仍未做：`selected` 取自 `flat` 而非 `filtered`，被折叠/筛掉的选择要等 fallback effect 挪到最近可见祖先 —— 旧有行为，一个提交的错位，未改。）
