## 「特别容易掉线：与服务器的连接已断开 · SSH 连接错误：read ECONNRESET」(2026-10-05)

**症状（用户报告）**：远程会话经常断，界面弹「与服务器的连接已断开（远端 Pi 已随会话结束）」，
detail 常见 `SSH 连接错误：read ECONNRESET` 或 `SSH 连接已断开（对端关闭）`；最近明显变频繁。

### 回路（Phase 1）：不需要复现网络，日志本身就是故障面

这台机器的 app 日志 `%APPDATA%/pipi/pipi-debug.log`（**时间戳是 UTC**，1.45MB / 11k 行）把每次
会话死亡都写成一行 `[rpc] tab rpc-N EXIT <code> stderr="…"`，并且 `[rpc] tab rpc-N CMD ssh=user@host`
能还原 tab→主机映射。所以回路 = **一行 awk 把 6 周的死亡事件变成按主机/按天的计数表**，
不依赖任何复现（掉线间隔 7s–8h，被动探针测不出来）。

```bash
# tab→host 映射 + 每次 EXIT 的对齐
awk '/\[rpc\] tab rpc-[0-9]+ CMD ssh=/{match($0,/tab (rpc-[0-9]+) CMD ssh=([^ ]+)/,m); host[m[1]]=m[2]}
     /\[rpc\] tab rpc-[0-9]+ EXIT/{match($0,/tab (rpc-[0-9]+) EXIT (-?[0-9]+)/,m); print substr($0,1,24), m[1], host[m[1]], m[2]}' pipi-debug.log
```

**结果（原始 EXIT 计数，含 app 退出伪报）**：

| 日期 | crscu@192.168.10.49（内网） | root@36.151.162.7（公网） |
|---|---|---|
| 09-24 … 09-30 | 1–5 / 天 | **0** |
| 10-02 | 1 | **0** |
| **10-03** | **11** | **9** |
| **10-04** | **15** | **5** |
| 10-05 | 1 | 0 |

两件事同时发生：内网主机掉线率 ×3–8，公网主机从「六周 0 次」变成「两天 14 次」。
**两台主机同一天一起回归** → 共享因子的权重高于「两台服务器各自出问题」。
（原始计数有约 1/3 是 app 退出/关 tab 时自己关传输产生的伪报，见下；按「≤10ms 成簇 + 7–10s 后
`[mem] startup`」过滤后 6 周共 **42 次真掉线**，回归比例不变。）

### 已证事实（逐条带证据）

**1. 死亡发生在传输层，不是 pi 崩溃。** `src/main/rpc-session.ts:102-161`：

| 代码 | 触发条件 | 写进 stderr 的文本 |
|---|---|---|
| `stream.once("exit", code)` | sshd 报了退出码 | （无） |
| `stream.once("close")` | 通道消失但没退出码 | （无） |
| `conn.on("error")` | ssh2 报错 | `SSH 连接错误：<msg>` |
| `conn.on("end")` | **收到对端 FIN** | `SSH 连接已断开（对端关闭）` |
| `conn.on("close")` | 连接关闭 | `SSH 连接已断开（网络中断或 keepalive 超时）` |

`reportDropped()` 有 `if (this.exitReported) return` 守卫，而 `stream.once("close")` 会先调
`reportExit(-1)`。所以**日志里出现「对端关闭」= TCP 层的 FIN 先到，通道/进程是被牵连死的**
（反过来说：`EXIT -1` 单独出现才是远端进程被信号杀掉）。这排除了「pi 自己崩了」——
pi 崩会带退出码 + stderr 里的报错文本，而不是干净的三行 bash 噪音。

**2. 不是我们的定时器、不是空闲超时。** 从最后一次发消息到死亡的间隔 7s–8h（变化极大，
最后一次实际使用后 3.5 分钟就死过一次），且与这些都不对齐：
keepalive（`keepaliveInterval: 15000 × 3` = 45s，6 周只出现 1 次 `Keepalive timeout`）、
90s 静默看门狗（`SEND_SILENCE_MS`，其出口是 `rpc_stalled` 事件，日志里 0 次）、
Clash 每 6 小时配置重载（11:20:47 / 17:19 / 23:19 …，掉线时间不落在这些刻度上）、
主进程卡死（`[mem] tick` 每 2 分钟一条，掉线时刻前后无缺口）。

**3. 网络路径本身今天没变差，但长连接死了。** 网络质量指标没有随回归一起上升：
`sftp op timeout` 峰值在 09-28（16 次），10-03 只有 4 次；`from-file FAILED` 10-03 才 10 次。
SFTP 和 RPC 走**同一条路径、同一个池**（都是 node `ssh2`），所以「路径整体劣化」解释不了
「短命 SFTP 没事、长命 RPC 会话死」这个组合。

**4. app 的 SSH 全部穿过本机 Clash/Mihomo 的 gvisor TUN 中继（已取证）。**

- `netstat -ano`：`198.18.0.1:14279 → 192.168.10.49:22` 属于 **electron (PID 29168)**，
  配对的 `10.18.60.38:14280 → 192.168.10.49:22` 属于 **verge-mihomo (PID 15772)**
  —— 即 app → TUN → mihomo 以 DIRECT 出网。
- mihomo 自己的日志（`%APPDATA%/io.github.clash-verge-rev.clash-verge-rev/logs/service/service_*.log`）
  有对应的 `[TCP] 198.18.0.1:* --> 192.168.10.49:22 using DIRECT`。
- 路由表：`0.0.0.0/0 → 198.18.0.2 via 198.18.0.1 metric 0` **压过** `0.0.0.0/0 → 10.18.60.1 metric 45`；
  而 **没有 `192.168.10.0/24` 的路由**（本地子网是 `10.18.60.0/22`，那台「内网」机其实在另一个
  网段、要走公司骨干）→ 所有新建到两台主机的 socket 都进 TUN。
- 配置：Clash Verge Rev 2.5.2，`mode: direct`、`tun.enable: true`、`auto-route: true`、
  **`stack: gvisor`**、`enhanced-mode: fake-ip`、`route-exclude-address: []`。
- 同一台机器上还有 Sangfor SSL VPN VNIC / DLP 代理（`ipc_proxy.exe`、`vpn.crscu.com.cn`）——
  公司出口是**第二层**可能发 RST 的中继。

> 注意 `mode: direct` 与 TUN **无关**：direct 只是规则命中 DIRECT，流量照样进 TUN 由 mihomo
> 的用户态栈转发。要让某目的地**不进 TUN**，要用 `route-exclude-address`（或一条更具体的路由）。

**5. 掉线成簇且按主机成簇**（10-03 21:03 本地时间，3 个 tab 在 31ms 内先后死，全在
`36.151.162.7`；同一秒 `rpc-1`（内网）活着）。且死亡前 2 分钟这台主机的 SFTP 操作
**60s 超时 ×4**——路径对它已经病了。这与「同一台服务器上所有会话被一起切断」一致。

**6. 掉线 = 会话结束 + 那一轮对话丢失。** `conn.exec()` 把 pi 挂在 SSH 通道上（`rpc-session.ts:114`，
没有 `setsid`/`noexec` 之类），传输一死 sshd 就 SIGHUP 整个进程组 → **远端 pi 进程随之消失**，
进行中的 agent turn 一起没了。而恢复只有手动一条路：`ChatPane.tsx:2591` 的「重新连接」按钮
（`markExited` 只把 `exited: true`；全局 grep 无 `reconnect`/自动重启逻辑，日志里恢复用的
`SPAWNED` 都是用户点击后 3 分钟才出现的）。**所以一次 1 秒的网络抖动 = 丢一轮工作 + 手动重连。**

### 尚未取证（谁发的 FIN/RST）

三个候选，都在本机之外，日志里都看不到：
(a) mihomo **gvisor 用户态栈**的中继（长连接 + 高并发下丢 flow，是这种栈的已知脆弱点）；
(b) **公司出口**（Sangfor VPN / 路由器 / NAT）的长连接策略；
(c) 远端 **sshd** 主动关（`ClientAlive*`、`MaxStartups`、重启、主机资源紧张——日志里见过
`pthread_create: Invalid argument` 这类远端资源信号）。

能一次定性的实验（**实验 2 已于同日完成 → 见「第二轮取证」；实验 1 仍需你点头**）：
1. **TUN 旁路对照**：给两台主机各加一条 /32 路由走物理网关（`route add 192.168.10.49 mask
   255.255.255.255 10.18.60.1 metric 1`，可 `route delete` 撤回；持久做法是 Clash 的
   `route-exclude-address`）。验证方式：`netstat` 里 app 的 :22 连接不再落在 `198.18.0.1`。
   预测：掉线率显著下降 → (a) 成立；照旧 → 指向 (b)/(c)。
2. **只读探测远端**（用 app 里已保存的凭据）：`journalctl -u sshd`、`dmesg`、`ss -s`、负载、
   `ulimit`。预测：sshd 日志里有 `Timeout, client not responding` / `Received disconnect` → (c)；
   sshd 那边什么都没记 → 掉线发生在它上游（(a)/(b)）。

### 处置（待用户确认后执行）

- **网络侧**：上面的实验 1（旁路 TUN）——这是目前唯一能「一次定性」的动作。
- **app 侧硬化**（不论网络结论如何都该做，且属于 AGENTS.md 的「稳定性就是产品」）：
  1. **别把「我们自己关传输」报成掉线**：`kill()`/重连/退出时 `conn.end()` → 对端 FIN 回来
     → `conn.on("end")` → `reportDropped("对端关闭")`，于是关 tab / 退 app 都会往
     `lastStderr` 里写一条**假掉线**（污染诊断，也让用户以为网络又断了）。加一个
     `expectClose` 标志，关的时候先置位。
  2. **传输死了要能自己回来**：加带退避的自动重连 + 重放（`resumeSession` 已经有手动路径，
     把它的重连部分接到 `tab:rpc-exit` 上，条件 = 非自愿关闭且不是 code 0）。
  3. **让远端 pi 不像纸糊的**：**pi 上游已经有 client/server 拆分**（未文档化的
     `experimental` 命名空间），这就是「掉线不死会话」需要的那个原语。核实结果：

     ```
     pi experimental server [--server-id <小写 uuidv4>] [--session-dir <dir>] [--provider X --model Y] [-e pkg]
     pi experimental client [--connect …] [--session-id <id>] [-c] [-r] [--provider] [--model] [-e] [prompt…]
     pi experimental            # → "Expected experimental command: server or client"
     ```

     `dist/experimental/server.d.ts` 的语义（比文档清楚）：

     | 类型 | 含义 |
     |---|---|
     | `RunningServer` | `{serverId, sessionDir, **socketPath**, server, **workerPids**, close()}` —— 会话跑在 **worker 进程**里 |
     | `activateServer()` | 「Ensure the selected logical server is reachable, **launching the current Pi installation if needed**」＝按需冷启动 |
     | `ServerLifetime` | 协调 operator / startup / client / worker 四种 hold（`keepAlive` 可让服务端在无客户端时继续存活） |
     | `runClient()` → `ClientResult` | `list` \| **`attached`** \| `prompted`；`onEvent` 收「**snapshot-ordered main-lane events**」 |

     并且是**已发布的独立包**（`@earendil-works/pi-client`、`pi-protocol`、`pi-server`、
     `pi-agent-core`）——即「用上游能力」，不是 fork。

     **落到我们的架构**（可行路径，按侵入度排序）：

     1. 远端 `pi experimental server --server-id <uuid> --session-dir <dir>` **脱离 SSH 会话启动**
        （`setsid`/`systemd-run --user --scope`/`tmux`），服务端 + worker 不随 SSH 死；
     2. app 侧用 **SSH 的 unix-socket 转发**把 `socketPath` 拉到本地（OpenSSH
        `-L local_sock:remote_sock`，ssh2 侧是 `forwardInStreamLocal`），再讲 socket 协议。
        掉线只需重开隧道 + 重新 attach（`kind: "attached"`），**turn 不丢**；
     3. 最低成本版本：远端跑 `pi experimental client --connect …` 把事件经 exec 通道转出来
        ——但它只输出 text delta（`runClient` 无 TUI 分支只 `process.stdout.write(event.frame.delta)`），
        **拿不到 tool 事件，喂不动我们的聊天视图**，只能当探测手段。

     副作用（顺带好处）：`ClientResult.kind === "list"`（+`SessionAddress`）说明「远程会话浏览」
     以后可以直接问服务端，而不是现在这样靠 SFTP 读别人的 JSONL。
     风险：`experimental` 命名空间，协议可能变；它自己也有 `radius-relay` / auth-token 语义，
     需要先做一次端到端验证（起 server、attach、断开重启隧道、再 attach）。
- **安全（本次不动，记成待办）**：`%APPDATA%/pipi/remote-history.json` 里口令是**明文**
  （两台主机都有）。按用户决定：不在这批改动里处理，留待办后统一改成 Electron
  `safeStorage`/DPAPI 并兼容读旧明文。

### 教训

- 「EXIT -1」不能当根因证据：它的来源至少有 4 个（无退出码的通道关闭、ssh 报错、对端 FIN、
  我们自己关），只有**stderr 里的那一行**能区分层次。先把这个语义搞清楚，再谈网络。
- 计数前先找**伪报**：`reportDropped` 在主动关闭时也会触发，退 app 时每 tab 写一条假掉线。
  不看 `[mem] startup` 和成簇特征就会把 66 次当 66 次真掉线。
- 有 TUN/系统代理的机器上，「我们的 SSH 到底走哪条路」不是配置说了算，是**路由表 + netstat +
  中继日志**说了算（`mode: direct` 完全不代表绕开 TUN）。
- 时间戳时区不统一（app 日志 UTC，mihomo 日志 +08:00）时，先对齐再谈相关性，否则会得出
  「重载导致掉线」这种假结论。

## 第二轮取证（2026-10-05 午后，全部只读）

### 1. 远端只读探测（`crscu@192.168.10.49`，用 app 已存凭据，未做任何改动）

### 2. 本机侧统计（排除伪因）

- **掉线前的空闲时长无规律**（1 s ~ 125 378 s 均匀分布）⇒ 否掉「中间盒 idle timeout」假设。
- **与 Clash `Configuration applied` 无关**（掉线落在配置应用后 5 分钟内的只有 2/60）⇒ 否掉「重载杀流」。
- **集群分类（用 `[mem] startup` ±60 s 判伪）**：
  - **伪掉线（退 app 写进去的）**：09-24 14:10、09-25 13:33/16:43/22:29、09-26 09:59/11:20、
    09-27 16:27、10-03 22:18、10-04 17:56/19:18；
  - **真掉线**：其余 ~37 次，其中「**同秒多 tab 全灭且无 app 重启**」：09-30 18:55:16（4 tab，LAN）、
    **10-03 21:03:14/15（3 tab，WAN，且同刻 LAN 的 rpc-1 存活）**、10-04 17:16:42/48/17:17:05（3 tab）。
- **归一化后才是真相**：`spawn` 10-03/04 为 8/14（此前 3~5），但 `prompt/spawn` 从 24 掉到 **1.6**
  ⇒ 不是「用得多」，而是**会话寿命塌了**（10-04 有多次 spawn 后几十秒内就死）。
- **机器上已有的天然对照组**：`ssh.exe`(PID 34576, `10.18.60.38:3069`) 与 FileZilla(PID 2380,
  `10.18.60.38:5630`) 的 :22 连接都是**直连**，端口比 app 的新连接老、状态仍是 ESTAB；
  而 app 的连接都是 `198.18.0.1:*`（走 TUN）。

### 3. 正在跑的判别实验：双路 A/B 探针（零配置改动）

- `tun` 臂＝默认路由（经 mihomo gvisor，与 app 同路）；`direct` 臂＝socket 绑 `10.18.60.38`（绕开 TUN）。
  同机、同主机、同时段，各持一条长连接。
- **每次死亡后立刻回服务器查这个四元组**：仍在 `ESTAB` ⇒ **FIN/RST 是路径注入的（服务器没发）**；
  不在了 ⇒ 服务器侧被拆。这一步不需要改路由就能定性「谁发的 FIN/RST」。
- 启动 25 s 实况（证明两臂确实分流）：`tun client=198.18.0.1:6735`（mihomo 出口 `10.18.60.38:6736`）、
  `direct client=10.18.60.38:6737`。日志：`%TEMP%\pipi-ab.log`（4 小时，脚本
  `%TEMP%\pipi-ab.cjs`，只读凭据读取，不改本机/远端配置）。

### 4. 第二轮结论

服务器侧静默 + 掉线无空闲/重载相关性 + **同秒多 tab 全灭**（且另一台主机同刻存活）⇒ 候选收敛为两个：

- **(a) 本机 TUN 用户态栈中继**（gvisor 是完整 TCP 端点，能在面向 app 的那半边发 FIN/RST，
  而 sshd 那边什么都看不到 —— 与全部观测一致，且它是唯一「从第一天就在path上」的新组件）；

### 6. 本轮新观测

1. **两条 A/B 臂的 RTT 一起涨到 ~50 ms，而 `minrtt` 都是 1.6–1.9 ms**（`tun` 50.9 / `direct` 49.2，逐分钟同步漂移）。

   与 TUN 无关**（若 TUN 用户态栈是瓶颈，只有 tun 臂会涨）。
2. **app 的 SFTP 租约连接（`peer=14280`）从 11:31:56 一直 ESTAB 到现在（33 min+），期间传了 8.4 MB**；
   而同期 tab 会话在 11:32:02 就死了。⇒ **掉线是「连接级」的，不是「到这台主机的路径级」的** ——
   同一时刻、同一 TUN、同一主机，一条活着一条死，排除「路径/TUN 整体崩」这种解释，
   指向**每条连接各自的命运**（各自的服务端进程命运 / 各自的 TCP 流状态）。
3. **天然对照（重要的阴性证据）**：`ssh.exe` 的直连 socket 已 **空闲存活 5.9 天**，
   FileZilla 的直连 socket 已 **空闲存活 7.8 天**（`lastrcv` = 5.1e8 ms / 6.7e8 ms 且仍 `ESTAB`）。
   两者都绕 TUN。⇒ **NAT/中间盒不会清理空闲长连接**（再次证伪 idle 老化假设），
   同时说明「同机直连 SSH 可以活好几天」。
4. 服务器整体状态（本窗口）：`load` 87.8 → 98.7 / 80 核；`oom_kill` 恒为 181（**本窗口无新 OOM**）；
   `resets sent` +202…+214 /min、`connection resets received` +120…+130 /min、
   `segments retransmitted` +500 /min；`pgmajfault` 几乎不动（swap 已抖完，进入稳态换页）。
5. 采样时刻服务器上**看不到任何 pi 进程**（`ps` 命中为空）——但此刻本来就没有活着的 tab，需在**下一次掉线后**
   立刻复查（快照器已带 `@@PIPROCS`），以回答最关键的产品问题：**掉线时远端 pi 是被一起杀掉，还是仍活着**。

### 7. 第三轮结论与待判分支

第三轮把候选进一步收窄，但出现了一个**新的张力**：观测 2 说明掉线是**逐连接**的精确死亡，
这与「路径/TUN 整体故障」不相容，却与「**服务端进程被逐个杀掉**」或「**TUN 用户态栈对某条具体流做重放/超时后强硬拆除**」
都相容。判别只剩两条，且都必须靠**下一次真实掉线**：

- **(a) 服务端拆的**：期望该 socket **立刻从服务器消失**（或 `oom_kill` +1）；
- **(b) 路径/TUN 拆的**：期望该 socket **仍 ESTAB、`lastrcv` 冻结**，服务器此后一直以为链路还在。

`pipi-watch.log` 会在下一次掉线时直接给出答案，无需改任何配置。

如果 (b) 成立，则**因果验证实验**仍是 TUN 旁路（`route add 192.168.10.49 mask 255.255.255.255 10.18.60.1`，
可 `route delete` 回退；持久化对应 Clash Verge 的 `route-exclude-address`）——**需要用户授权**。

### 8. 产品侧的确定结论（与上面哪个分支成立无关）

1. **掉线必丢当前回合**：远端 pi 跑在 `conn.exec()` 下面（`src/main/rpc-session.ts:114`，无 `setsid`/`nohup`/tmux），
   传输一断 → 会话被 SIGHUP → 进行中的回合直接消失。这是「特别容易掉线而且特别疼」体验的真正来源。
2. **无自动重连**：日志里 `重连|reconnect|恢复` 命中 0；恢复全靠手动点「重新连接」（`ChatPane.tsx:2591`）。
3. **约 25/60 条「掉线」是假的**：app 自己退出/重启/关 tab 时也会写 EXIT（已按 `[mem] startup` 时间窗分类），
   需要用 `expectClose` 标志区分「主动关」与「被动掉」，否则日志与用户感受都会被污染。
4. 正解方向是把「会话存续」从「SSH 通道」里拆出来：`pi experimental server`（unix socket + `--server-id`）
   让传输断开变成「重新 attach」，而不是「回合蒸发」。

### 11. 方法论修正：金信号对 TUN 连接失效

第三轮设计的判据是「掉线后服务器四元组**仍在 ESTAB** ⇒ 路径侧注入 FIN/RST；**消失** ⇒ 服务器侧拆的」。
本轮发现它对 TUN 连接**没有判别力**：mihomo 是**用户态中继**，服务器看到的那条 socket 是 mihomo 自己发起的
（`198.18.0.1:14279`(app↔mihomo) ↔ `10.18.60.38:14280`(mihomo↔sshd)）。任何一侧被拆，mihomo 都会把另一侧一起关掉 ——
所以 **TUN 连接的服务器侧 socket 消失，既可能是服务器拆的，也可能是 TUN 拆的**。
（`tun` 臂那次 `服务器上仍然ESTAB=no` 因此**不能**读成「服务器主动拆」。）

判据只在**无中继的直连**（`ssh.exe`/FileZilla/`direct` 臂，客户端就是真实端点）上成立。
要判别 app 的掉线，必须用**旁路之后的直连 app 连接**，或改用「app 侧 socket 状态 + 服务器侧 socket 状态 + mihomo 中继腿」三条一起看。

### 14. 受控掉线实测：自动重连按设计工作（2026-10-05 12:26，一次主动 kill）

方法：app 重启（新 PID 38084，12:21:06；已核对 `out/main/index.js` 里含 `rpc_reconnecting`/`RECONNECTED transport`/`closed by app`）

→ `kill -TERM` 它。这复现的正是历史 39/60 次的「**对端关闭**」签名（TCP FIN 先于通道状态）。

app 侧（`pipi-debug.log`，UTC）：

04:26:57.512Z [rpc] tab rpc-1 RECONNECT #1 in 1000ms
04:26:58.545Z [rpc] tab rpc-1 CMD ssh=crscu@192.168.10.49 ...（同一个 sessionFile）

04:27:12.129Z [transcript] tab rpc-1 from-file OK messages=1318 tail=120

远端（`%TEMP%\pipi-drop.cjs`，kill 后每 5 s 快照 ×8）：

- 被 kill 的 sshd 子进程 `1135583` 与其 `pi`（pid 1135604）**一起消失**，取而代之的是新会话 `sshd 1146777 → pi 1146800`；
- 同一时刻另一个 sshd 子进程（`1134995`，SFTP 租约）**毫发无损** ⇒ 又一次印证「掉线是逐连接事件」；

结论：

1. **自动重连实测通过**：首次退避 1 s、同一 tab id、同一 sessionFile、1.5 s 内重建传输、7 s 内收到首个 RPC 帧、13 s 内 transcript 重拉 1318 条。

3. **「传输层先死 → 远端 pi 被 SIGHUP」的因果链现在可以本机按需复现**（不必等真实掉线）。

> 工具：`node %TEMP%\pipi-drop.cjs list|kill`。`kill` 模式末尾那句「^^ 仍有 pi 存活」是脚本的**朴素告警**（它看到的是重连后的**新** pi），

**待测（用户随时可做）：假掉线抑制。** 做法：在 app 里关掉 `rpc-1` 这个 tab。判据：
日志里**不应**新增 `EXIT -1`（旧代码在主动 kill 时也会走 `reportDropped` → `EXIT -1`，这正是历史掉线统计被高估的来源），

### 15. 教训（续）

1. **「瞬间全灭」是组件拆除的签名，不是网络的签名**：一条链路上所有连接同秒死亡、且该组件之外的同目标连接毫发无损，
   先怀疑那个共享组件（这里是 TUN 的用户态栈），而不是中间网络。
2. **判别器要先验证自己的判别力**：中继（用户态代理）会把「谁拆的」这个信息抹平 —— 设计金信号时必须先问
   「这个观测在中继存在时还区分得开吗」。
3. **对表要对着组件的日志表，而不是对着自己的感觉**：`[Core] Configuration applied`（Verge 应用日志）
   == `Start initial configuration in progress`（内核日志）== 一次真实拆栈；「6 小时重载」这种规律性事件
   最容易被误当成随机掉线的解释，而对表只需一次脚本就能证伪（本次 47 条 vs 6 条，全部落在分钟级邻域之外）。
   反面教训同时成立：第一次取证时把「拆栈」误读成「例行重载」——**同一行日志在不同前提（TUN 开/关）下含义不同，
   取证必须同时确认真实生效的配置**（这次是 `verge.yaml enable_tun_mode` + 网卡列表 + 默认路由三条才对上）。
4. **修「体验」不需要等根因**：掉线本身没定位完，但「掉了要能自己回来」「别把主动关闭报成掉线」是确定性改进，
   应当先落地（§12.1）；根因取证（§11 的直连判别）与产品修复可以并行。
5. **「自造掉线」是最便宜的判别器**：主动 kill 对端 sshd 子进程 = 无限次复现历史签名，用来验证恢复路径（§14），
   比等一次真实掉线（0.3 次/小时）快两个数量级。
6. 附带：`%TEMP%\pipi-watch.cjs` 的 `netstat -s` 解析在本轮全部返回 `undefined`（`resetsSent=undefined`），
   `ss`/`netstat` 字段顺序假设不可靠 —— 采样器自身的指标要么校验、要么显式标注缺失，否则会静默变成假的「0」。
7. 附带：`sshd` 的 socket 是从 root 父进程继承下来的，所以**非 root 的 `ss -tnp` 看不到 pid**
   （本次想用它精确定位 sshd 子进程，失败）——只能靠 `ps` 的 ppid 链或 `pstree` 反推。

## WSL 目标的 `pi` 解析会漏到 Windows 主机 PATH（slice 2 附带发现，**未修**）

**症状（本机实测，非用户报告）**：把「WSL 目标上的 pi 版本」交给新 seam 探测时，`Ubuntu-22.04` 返回 `0.85.1`，
而同一发行版里手工跑 `bash -ic 'pi --version'` 返回 `0.85.0`。同一个问题、两个答案。

**根因**：WSL 互操作会把**整条 Windows PATH** 翻译成 `/mnt/...` 追加进发行版的 PATH（标准行为，只有 `/etc/wsl.conf`
的 `[interop] appendWindowsPath=false` 能关）。于是 `pi`、`node`、`npm` 都可能解析到 Windows 侧：

```
$ wsl -d Ubuntu-22.04 -- bash -ic 'echo "$PATH" | tr : "\n" | grep -n "^/mnt"'
10:/mnt/c/Users/chang/miniconda3/envs/py311
...
15:/mnt/c/Users/chang/.pi/agent/bin
...
$ wsl -d Ubuntu-22.04 -- bash -ic 'command -v pi; pi --version'
/mnt/c/Users/chang/AppData/Roaming/npm/pi     ← Windows 全局 pi
0.85.0
```

`0.85.1`（app 捆绑版本）来自调用进程 PATH 里的宿主机目录被翻译过去：本次那个进程的 PATH 含
`D:\其余文件\项目\agent\node_modules\.bin` → WSL 里就是 `/mnt/d/其余文件/项目/agent/node_modules/.bin/pi`，
即 **app 自己仓库里的捆绑 pi**。也就是说：探测结果可能完全由宿主机（乃至 app 自身）决定，与发行版装没装 pi 无关。

**这不是 slice 2 引入的。** `git show HEAD:src/main/update-check.ts:630` 的旧 WSL 探测同样是
`spawn(findWslBin(), [...'-d', distro, '--', 'bash', '-ic', targetPiCommand(...)], { windowsHide: true, stdio })`
——没有 `env` 也没有 `cwd`，继承的是一模一样的环境。slice 2 只是把这份行为原样接到了 seam 上。

**为什么当时不改**：漏的不止探针。**WSL 标签页与 WSL 聊天传输用的是同一套环境**
（`pty.ts` `createWslTab` 的 `pty.spawn(wslBin, ['-d', d, '--', 'bash', '-ic', ...], { cwd: process.cwd(), env: {...process.env} })`、
`rpc-session.ts:521` 的 `bash -ic wslCmd`），所以「探针解析到的 pi」**正是标签页真的会启动的那个 pi**。
只给探针加 PATH 清洗会让两者分叉——探针报「发行版里的 pi」，标签页跑「主机上的 pi」——恰是 ADR 0001 要消灭的
「一处目标、两种真相」。要修就得三处一起修（`pty.ts` + `rpc-session.ts` + 传输绑定），而那正是 ADR 0001
明确留给后续的 **exec/运行通道**决策，不属于 ADR 0007 的行为保持范围。

**实际影响（窄但真实）**：发行版里**没有**装 pi 时（或没装 node/npm），探测会报「存在」并给出宿主机的版本号，
于是「已对齐/需要更新」的判断与安装位置（`command -v pi` → `/mnt/c/...`）都会指向 Windows 侧。常见情形
（用户按 nvm 装在 `~/.nvm/.../bin`）里，发行版自己的 PATH 项排在追加的 `/mnt/*` 之前，所以解析正确——这也是
为什么这个坑至今没被报上来。

**教训**：`-ic` 拿到的 PATH 不是「发行版的 PATH」，而是「发行版 PATH + 宿主机 PATH」。任何「在这个发行版里查
一个命令」的判断都要先问自己：会不会查到了宿主机。

## 追记（同日，修复时发现）：`wsl.exe --` 会把 `$VAR` 预展开成空

动手修上面的 PATH 泄漏时（ADR 0010），第一版「PATH 清洗片段」在真机 spawn 下不生效，
而用 stdin/脚本文件跑同一段内容却完全正常。逐层二分到最小复现：

```
$ wsl.exe -d Ubuntu-22.04 -- bash -c 'X=abc; echo "[$X]"'
[]                      ← $X 被展开成空，X=abc 的赋值没生效
$ wsl.exe -d Ubuntu-22.04 --exec /usr/bin/bash -c 'X=abc; echo "[$X]"'
[abc]                   ← --exec 模式下原样到达发行版 bash
```

**根因**：`wsl.exe -d <distro> -- <cmd…>` 的 `--` 之后并非「原样执行」——wsl.exe 仍按
**Windows 侧**的环境对参数做 `$VAR` 预展开，Windows 侧不存在的变量一律变**空串**，
于是命令里的 `$( )`、`$P`、`${P#~/}` 全部失真。`$USER` 之所以「有值」，只是因为它在
Windows 侧环境恰好不存在、没得展开；`$PATH` 被展开成 Windows PATH 后经 `/mnt` 翻译
也能「碰巧」工作，掩盖了失真。

**波及面**：产品里所有走 `-- bash -ic` 的 WSL 命令——`targetPiCommand` 的 base64 cwd
解析（`P=$(…| base64 -d)`）、`buildRemoteAlignCommand` 的 `P=$(command -v pi)`、
聊天传输与终端 pty 的 `cd`——在 `--` 模式下从来没有真正按写的语义执行过。此前
「WSL 探测/对齐能用」是运气：无 cwd 时不走 `P=…` 那段，而 `P=$(command -v pi)` 被展开
成空后 `case ""` 恰好落进 `*)` 分支装 npm 版。

**处置**：WSL argv 统一改为 `wsl.exe -d <distro> --exec /bin/bash -ic '<命令>'`
（`wsl-shell.ts` 的 `wslArgv`），命令文本前置 PATH 清洗（`wslInnerCommand`）。
探针、对齐、聊天传输、终端 pty 四个消费者同一形状。真机回归：Ubuntu-22.04 清洗后
`pi=NONE`（distro 确实没装 pi，不再是宿主的 0.85.0）、node/npm=nvm v24.14.0、
base64 cwd 正确 `cd /home/lc`。

**教训**：「`--` 结束选项解析」只保证 wsl.exe 自己不再吃参数，**不保证参数原样到达
Linux 侧**。跨这条边界的任何 `$` 都要假设会被 Windows 侧先动一次；要么 `--exec`，
要么把可展开的内容全部 base64 化（`targetPiCommand` 的先例）。
