## 三种模式（auto/plan/edit）整体删除，回到官方 pi 的单一 auto 模式 (2026-09-27)

用户决定：「彻底删除这三种模式，聊天页里的模式也删除，回归到最原始的 pi agent 的单一 auto 模式」。
（上一个决定是删范围：连「写操作授权弹窗」一起删 —— 官方 pi 特意不做权限弹窗，工具直接执行。）

**删掉的东西**
- `src/main/extensions/pipi-mode-switch.ts`（46.9KB）：`/mode` `/plan` `/todos`、plan 只读守卫、
  edit 逐条确认、模式环境导出、`[DONE:n]` 计划执行；以及 `agents/planner.md`、
  `prompts/scout-and-plan.md`（上一轮的 scout→planner 分发）。
- 聊天页：`panes/useSessionMode.ts`、`panes/mode-status.ts`、模式三档切换按钮、计划待办浮层、
  `chatStore` 的 `sessionMode/sessionModeProgress/sessionModeTodos/sessionModeSwitching` 四个字段
  与 `mode_status` 事件分支、ChatPane 里 `pipi-mode:` 状态/`pipi-mode-todos` 控件的桥接、
  `styles.css` 的 13 条 `.chat-mode-*` 规则。
- 测试：`mode-confirm-plain-language.test.ts`（22 例）+ 并发会话新建的 `mode-status.test.ts`、
  `mode-switch-extension.test.ts`。测试从 827 降到 791（删掉的都是模式自身的契约）。
- 保留：`UiDialog` 与 `shared/confirm-detail.ts`（`splitConfirmMessage`）—— 它们是**通用**的：
  任何 pi 扩展（含用户自装）调 `ctx.ui.confirm` 时仍会渲染出「一句人话 + ▸ 查看具体内容」。

**新增：退役机制（这次删除能否真正生效的关键）**
pi 会**自动加载 `~/.pi/agent/extensions/` 下的每个 .ts** —— 光"不再分发"是不够的：老扩展还在磁盘上
继续跑（我们只是不再渲染它的 UI：提示、拦截、弹窗照旧发生）。所以：
- `RETIRED_FILES`（`extension-sync.ts`）：记录不再分发、必须**删除**的文件，每条带
  `sha256`（当年发出的确切字节）+ 若干**无空格**标记（老版本也能认出来）。
- `shouldRetire(content, spec)`：**哈希相同 或 全部标记命中**才认定是我们的文件；用户自己写/改过的
  文件一律不动，只在日志里说明。
- 三条路径都接了：本机启动（`retireShippedFiles()`，index.ts 与 `ensureShippedExtensions()` 并列）、
  SFTP（先 retire 再上传，`client.delete(path, true)`）、ssh 一次性安装命令
  （`( test -f path && grep -q $(echo <b64> | base64 -d) path && rm -f path || true )`，保持全程无引号）。

**顺带修的**：`src/main/index.ts` 与 `原 CONTEXT.md` 里各有一个**裸 NUL 字节**（写在模板串/散文里的
`\x00`），导致 `grep` 把这两个文件当二进制。改成转义写法后运行时字符串完全不变，文件恢复可 grep。（**这条只对 `src/main/index.ts` 做到了**：原 CONTEXT.md 里那两个裸 NUL 一直留到 2026-09-30 才清掉，其中就有一个写在本条记录自己的引文里。）

**教训**：删除一个"平台会自己加载"的东西时，删除动作要包含**卸载已安装的副本**；只停止分发会让
旧行为永远留在用户机器上（本机 + 每台远程服务器）。
