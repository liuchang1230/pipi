## 「/compact 其实已经压缩好了，但聊天视图一直显示『正在压缩上下文』」(2026-10-04)

**症状（用户报告）**：在聊天视图用 `/compact` 压缩上下文，压缩**确实完成了**（用户能判断它完成了），
但界面**一直**显示「正在压缩上下文」，不消失。

### 回路（Phase 1）：不用起 app，store 就是故障面

这是一个纯状态机 bug：聊天视图那行字是 `turn.phase` 的函数（`ChatPane.tsx` 的 `phaseLabel[phase]`），
而 `turn.phase` 完全由 `chatStore.applyEvent` 从 pi 的事件推出来。所以回路 = **按顺序喂 pi 的真实事件形状，
断言终态**，跑一次 0.5s：

```
apply([{type:"compaction_start", reason:"manual"},
       {type:"compaction_end", reason:"manual", result:{summary:"s", tokensBefore:150000, estimatedTokensAfter:32000}}])
→ expect(turn.phase).toBe("completed")     // 修前：'compacting'（红）
```

修前一次跑出 **6 个红**（3 个是 `turn.phase` 的出口、3 个是两种摘要形状的渲染），修后 74/74 绿；
第 74 条（取消压缩要收尾 abort）是复查时发现二阶 bug 后补的。

### 根因：`/compact` 不是一次 agent run，没人替它收尾

事件链（`node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js`；本地 SDK worker 与远程
`pi --mode rpc` 走的是同一条事件流）：

| 谁 | 做了什么 | 后果 |
|---|---|---|
| `compaction_start` | store 置 `compacting: true` **且** `turn: {phase:"compacting"}` | 底部状态栏进入活跃态 |
| `compaction_end`（成功） | store 置 `compacting: false`，但 `turn` 走 `: st.turn` —— **phase 留在 `"compacting"`** | 时间线横幅清了，**底部状态栏没清** |
| pi 的 `compact()` | 只发 `compaction_start` / `compaction_end`，**从不发 `agent_start` / `agent_settled`** | 没有任何后续事件能把它推走 |
| `state_ready`（任何 get_state 快照） | `pendingTurnPhases` **包含 `"compacting"`** → 刻意保留 | 连周期探针也救不回来 |
| `ChatPane` 的 `phaseActive` | `!["ready","completed","failed","exited","cancelled"].includes(phase)` | `"compacting"` 是活跃 → 小转轮 + 「已运行 Xs」一直涨 |

所以用户看到的是**两个指示器里的第二个**：时间线里的「正在压缩上下文（compaction）…已 Xs」横幅按 `compacting`
布尔量，`compaction_end` 一到就清了；而输入框上方那行「正在压缩上下文…」按 `turn.phase`，**永远留着**，
直到用户碰巧发下一条消息（`agent_start` 才改 phase）。

### 顺带查清：pi 给了摘要，是我们没接

用户问「pi 终端会不会返回摘要、聊天视图怎么拿 pi 的反应」。核实结果——**pi 三个出口都给了**：

1. **终端 UI**：`interactive-mode.js:2754` 收到带 `result` 的 `compaction_end` 后清空聊天区、
   `buildContextEntries()` 重绘，并追加 `createCompactionSummaryMessage(result.summary, tokensBefore)`，
   有 `usage` 再加一条计费提示；
2. **事件**：`compaction_end.result.summary` 就是摘要全文；
3. **文件**：`session-manager.js:818 appendCompaction()` 落盘 `type:"compaction"` 条目，随后
   `agent-session.js:1541` `this.agent.state.messages = sessionContext.messages` —— 模型上下文从此以它开头。

我们的聊天视图有**两条通道**，但把这四件事都丢了：

- **推送（实时事件）**：`session.subscribe`（本地 SDK）/`pi --mode rpc` stdout → `forwardEvent` →
  IPC `tab:rpc-event:<tabId>` → `chatStore.applyEvent`。→ 摘要文本只留了两个数字
  （`lastCompactionSummary = {before, after}`），而且**连这两个数字都没有任何 UI 读**；
- **拉取（历史快照）**：`requestHistory` → 远程/WSL 读 session 文件（`shared/transcript.ts:111` 把
  `type:"compaction"` 映射成 `{role:"compactionSummary"}`）、本地 tab 回退 RPC `get_messages`
  （此时摘要是一条**被 `<summary>` 包起来的 user 消息**）。→ `initMessages` 只认
  `user`/`assistant`/`toolResult`：**文件形状被静默丢弃**，而 live 形状被渲染成一大段英文 **user 气泡**
  （「The conversation history before this point was compacted into the following summary: …」）；
- **并且压缩后没有任何东西触发 `requestHistory`**（触发点只有 mount/state_ready/fork/导航/new/clone）。

即：pi 举着「压缩完成，这是摘要」的牌子，我们既没接牌子、也没重新去档案里读，而且转圈的开关还忘了关。

**二阶 bug（同一根因）**：用户按「停止」取消压缩时，`abortOutstanding` 一直为真（`abortResolved` 只在
`agent_start`/`agent_settled`/abort 自己的 message_end 上收尾，而压缩没有这些）→ 下一条消息被
`sendPrompt` 塞进 `deferredPrompts` 等一个**永远不会来的 settle**，最多干等 8s（`DEFER_AFTER_ABORT_MS`）。

### 处置

`src/renderer/src/stores/chatStore.ts`（`compaction_end` 分支）：

- 失败 → `failed`（原有）；**取消 → `cancelled` + `abortResolved: true`**（收尾那个二阶 bug）；
- **`isStreaming` 为真 → `thinking`**：自动压缩（overflow）发生在 run 中间，agent 紧接着继续，这里给终态会
  在回合中间闪「✓ Agent 已完成」；
- 否则（手动 `/compact`）→ `completed` + `detail: "上下文已压缩"`，并记下 pi 的摘要全文 / reason / 时间
  （`lastCompactionSummary`）。

`src/renderer/src/panes/ChatPane.tsx`：

- `phaseLabel.completed` 改为 `state?.turn.detail ?? "✓ Agent 已完成"`（复用既有的 2.5s 完成闪烁）；
- 时间线新增**常驻不脉冲**的「✓ 上下文已压缩：150k → 32k tokens」通知条 + 「查看摘要」（展开 pi 摘要原文）
  + 「知道了」（按 `at` 时间戳逐次消退，不用全局开关）；**下一次历史快照到达即自动退场**
  （通知条只是过渡形态，快照里的 `<details>` 行才是长期形态：用户 `/new` 或导航到压缩之前的
  分支后，它不能继续声称「上下文已压缩」）；
- 历史里的压缩摘要（两种形状）渲染成独立的 `<details> 上下文摘要` 行，不再是 user 气泡、也不再被丢弃
  （`shared/transcript.ts` 新增 `compactionSummaryOf`，两种形状的分辨逻辑与 pi 的
  `COMPACTION_MESSAGES` 前缀一起放在这个「pi 语义镜像」模块里）。

**刻意没做**：压缩后不自动重取历史。pi 的 TUI 会重绘成压缩后的上下文（旧消息从视图里消失），
我们保留用户已看到的对话，用通知条说清「模型现在看到的是什么」。若将来要对齐，`requestHistory` 的
在飞闸门与 `initMessages` 的替换语义需要先想清竞态。

### 教训

1. **不是 agent run 的操作，没有 `agent_settled` 兜底**——`/compact`（还有 `/reload` 一类扩展命令、
   模型同步）都是「发件事就走」。任何在 `*_start` 里改 `turn.phase` 的地方，**必须在同一个功能的 `*_end`
   里给出出口**，否则 phase 就是一条单行道。之前 model-sync 已经踩过一次同样的坑
   （「扩展命令的『回执』是 prompt 响应帧，不是 agent_settled」）。
2. **「对端有数据」≠「我们接了数据」**：这次 pi 的三条出口齐全，故障全部在我们这一侧
   （丢弃 + 无 UI + 忘了复位）。排查「界面不反映真实状态」时，先数清**信息从对端到像素要经过几次转手**
   （事件订阅 → IPC → store → 选择器 → 组件），逐段问「这一段丢了吗」。
3. **同一状态的两个指示器要走同一个字段**：横幅读 `compacting`、底部读 `turn.phase`，于是只清一个的 bug
   看起来像「清了又没清」。状态源收敛比多写一个复位更值钱。

## 「打开会话（尤其远程）『正在启动 pi…』一闪就没了，历史过很久才出现，看起来像卡住」(2026-10-04)

**症状（用户报告）**：打开一个会话（**远程更明显**）时，聊天区先显示「正在启动 pi…」，
这行字**很快就消失**，而历史/上下文要过很久才出现——中间那段时间就是**空白**，看起来像卡住了。
用户的要求：那行提示应该**留到上下文出现为止**。

### 回路（Phase 1）：store 就是故障面

可见面是「聊天时间线在没有内容时显示什么」，它是 `chatStore.states[tabId]` 的布尔 +
`tasksStore` 相位的函数 → 回路 = 按真实顺序喂 store，断言决策函数的输出。**不需要起 app**。

用真实的远程打开顺序构造：`openSession` → `ensure` → `markHistoryLoading`（`historyLoaded=false`）
→ 任务 `begin` → `applyEvent(state_ready)`（`booted=true`，暖链路 ~2s）→ 若干秒后才 `initMessages`。
先写 `panes/__tests__/chat-transcript-wait.test.ts`：第一版 11 例里 **5 例红**，红的正是症状本身
（`state_ready` 之后决策给出 `'empty'`，也就是"这个会话是空的"，而不是"还在读"）。

### 根因：等待的可见期挂在了错误的信号上

改前 `ChatPane.tsx` 的 `ChatTimeline` 里三处并列条件：

```tsx
{!timeline.booted && !bootTimedOut && <div className="chat-placeholder">{bootStage === "connecting" ? "正在连接远程 Pi…" : "正在启动 Pi…"}</div>}
{!timeline.booted && bootTimedOut && <div className="chat-error-banner">pi 启动超时…</div>}
{messages.length === 0 && timeline.booted && <div className="chat-placeholder">输入问题开始对话…</div>}
```

1. **主因：提示的存在期 = `booted`，而 `booted` 的翻转与历史的到达是两条独立的路。**
   `booted` 由 `state_ready`（或 SDK 的 `get_state` 应答）置位，暖链路约 **2s**；历史走**另一条更慢的路**
   （file-first：远程/WSL 读会话文件，SFTP/ssh，实测 **17–45s**；预算 60s 文件 + 120s RPC）。
   于是 `state_ready` 一到，那行字被撤销，而内容还在路上 → 空白。
   **「进程就绪」从来不是「会话可读」**——这是本次故障的根因表述。
2. **二阶（让空白伪装成正常）**：`messages.length === 0 && booted` 把**同一个窗口**当成"空会话"，
   在等待期间盖上「输入问题开始对话（鼠标可直接点击、选中、编辑输入内容）」。一块空白 + 一句"你可以开始输入"，
   用户得到的结论不是"在加载"，而是"坏了"。
3. `historyLoaded`（`markHistoryLoading` 置 false、`initMessages` 置 true）本来就是那个**缺失的信号**，
   而改前它**只**被 `state_ready` 分支用来做重复请求守卫（`if (!cur?.historyLoaded) requestHistory()`），
   **没有任何 UI 读它**。和「压缩」那次同款：状态字段存在、没人读，界面只能靠推断。

（被证伪的假设：`bootStage`/`app_phase` 事件被丢弃 → 否，`bootStage` 一直在 store 里且接得正确；
它只是同样在 `booted` 翻起时被**整体**撤掉。）

### 处置

- 新增纯模块 `src/renderer/src/panes/chat-transcript-wait.ts`：`deriveTranscriptWait(input)` 一张决策表，
  五种输出（`none` / `empty` / `boot-*` / `history{retry}` / `history-failed{detail,hint,retry}`）。
  优先级：**已有内容 > 进程已退出 > 进程未就绪 > 历史未到 > 真的空**。
  文案也在模块里，单测断言的就是**用户看到的那句话**。
- **等待本身是一个任务**（不变量 #2）：`requestHistory` 里 `begin("chat:history:<tabId>", {label, stallMs:15s, failMs:200s, retry})`；
  在 `finally` 里（闸门 `settle()` 之后、"非补跑"分支）`settle(taskKey, applied ? undefined : {error})`——
  **只有历史真的落地才 `done`**；两条路都走完仍没拿到 → 终态失败 +「重新读取」，不会再出现"永远正在读取"。
  - T1=15s 是**诚实阈值**（开始报"已等待 Ns"并给重试），T2=200s **高于请求自身的预算**（60s 文件 + 120s RPC），
    所以"慢但健康"的多 MB 下载永远不会被画成失败。
  - 补跑分支（`rerun`）**不 settle**：它自己会 `begin({restart:true})`，提前结算会把新一轮等待标成完成。
- `ChatTimeline` 改为 `useTask(historyTaskKey(tabId))` + deriver 渲染；`historyLoaded`/`exited` 进 `useShallow` 选择器；
  等待期间 1s tick（冻住的「已等待 Ns」与冻住的转圈是同一种谎）。
- 文案：boot 阶段仍是「正在启动 Pi…」，进入历史阶段改说「正在读取会话历史…」——比让"启动"一直挂着准确；
  失败面直接用任务自带的 title/cause/hint（不变量 #8）。
- 测试：`chat-transcript-wait.test.ts`（11 例，含 store 驱动的真实序列回归）+ `no-eternal-spinner.test.ts`
  新增一例（画到一半的下载：T1 报"已等待"、T2 变终态且带 retry）。`scripts/chat-wsl-smoke.mjs` 的两行诊断从
  "placeholder 没了吗"改成打印那行字的**内容**（现在 5s 时它**应该**还在）。

### 教训

1. **等待的可见期必须挂在"内容到达"上，不能挂在"对端就绪"上。** 多阶段启动（连接 → 进程就绪 → 数据到达）里，
   后一阶段不能复用前一阶段的证据：那个"最后一步完成"的信号必须是**最后一步自己的**信号（这里是 `historyLoaded`）。
   这类 bug 的症状永远不会是报错，而是"提示提前消失 + 一片空白"。
2. **"没有内容"与"内容还没到"必须分开表达。** `messages.length === 0` 在加载期间同样为真，
   拿它当"空会话"的判据，等于在加载时宣布"这儿什么都没有"。空态判据必须包含"加载已经结束"。
3. 又一次验证「**字段存在但没人读 = 界面靠推断**」。排查"界面不反映真实状态"时先问：
   这个状态的唯一真相是什么、**有几个读者**。
4. 一个状态两个消费者要一起收尾：这次"读取中"由 `historyLoaded`（重复请求守卫）与任务（可见等待）共同拥有，
   两者都落在 `finally` 的同一条路径上，才没有出现「清了又没清」（对比上一节压缩那次的教训 3）。

## 「打开会话别让我自己往下滚」：快照落地欠一次跳转 (2026-10-04)

**症状（用户报告）**：聊天视图每次打开一个会话都停在**最旧**的那条上，用户必须自己滚到最新。

**根因**：时间线是**尾锚定**的（`messages.slice(-visibleCount)`），但容器是新建的（`scrollTop = 0`）
→ 落在"已挂载那 60 条"的**开头**。而唯一会写 `scrollTop` 的实时跟随有这个前置判断：

```js
if (distanceFromBottom > 60 || …) return;   // 只轻推已经贴近底部的视口
```

也就是"只跟已经在底部的读者走"——而刚打开时距离底部**最远**，恰好被排除在外。
（这句 `if (!isStreaming) return  // no live content → the browser owns the position`
让历史快照落地时干脆没有任何定位动作。）

**处置**：新增纯模块 `src/renderer/src/panes/chat-scroll.ts`：快照落地欠**一次**跳转（`owing`），
规则有两条反悔条款——① 只在"**当时没有已挂载内容**"或"**读者本来就在底部**"时才花掉这笔债；
读者滚上去看旧消息时快照替换（重试 / fork / 导航）**只清债、不抢位置**；
② `clientHeight === 0`（还没布局）时**留着债**，下一次 pass 再跳（在未布局的盒子上写 `scrollTop` 是静默空操作）。
组件侧：`ChatTimeline` 里 `jumpRef`/`mountedCountRef` + 一个 **layout effect**（`[messages, historyLoaded]`），
在**绘制前**完成定位，因此不会有"先看到最旧、再闪到最新"的抖动。测试 `chat-scroll.test.ts`（6 例）。
诊断脚本 `diagnose-chat-scroll.mjs` 的 `boot` 探针补 `scrollTop/distanceFromBottom`（期望 ≈0）。

**教训**：「跟随底部」与「打开时定位到底部」是两件事——跟随的前提是"读者已经在底部"，而打开时读者
**不在**底部（他甚至还没看到内容）。把后者当成前者的一个分支，症状就是"打开总停在最旧的"。
凡是"新数据到达后视口去哪"的逻辑，都要分别回答**"读者原本在哪"**（保留）与**"这里有没有位置可保留"**（跳到最新）。
