## 远程报错「Cannot find module …/openai-completions-JXDDPZ23.js」（root@36.151.162.7:40008）

**症状**：远程会话弹「⚠ 模型错误：Cannot find module '/root/.local/share/pi-node/node-v22.23.2-linux-arm64/lib/node_modules/@earendil-works/pi-coding-agent/dist/bundle/chunks/openai-completions-JXDDPZ23.js' imported from …/chunk-5OEJBNHG.js」。

**取证**（ssh2 密码通道，凭据全程只在 env 流转、不打印不落盘）：

1. 安装是 **pi.dev 官方安装器的托管树**（`~/.local/share/pi-node/node-v22.23.2-linux-arm64/`），`.bashrc:106` 把它的 bin 前置进 PATH。原版 0.84.4（settings.json 的 `lastChangelogVersion`）。
2. **全部 dist 文件时间戳 = 当天 10:13**（用户当时正连着会话）→ 升级发生在会话活着的时候。
3. 报错时刻：旧进程（`chunk-5OEJBNHG.js` 属旧一代构建）惰性加载 `openai-completions-JXDDPZ23.js` 时，磁盘上已是新代构建（只有 `openai-completions-OSRCWAAA.js`）——撞上升級的中间态。
4. 磁盘现状自洽：全 dist grep 无任何 `JXDDPZ23` 引用，`chunk-5OEJBNHG.js` 也已不存在 → 升级最终写完，只有进程受害。

**根因**：pipi 的远程对齐命令（`buildRemoteAlignCommand`）在登录 shell 里跑 `npm install -g @earendil-works/pi-coding-agent@pin`；但该机 PATH 前置 pi-node/bin，`npm` 解析到**托管树自带的 npm** → 装进托管树内部、就地重写活着的安装。pi.dev 托管安装的正规升级通道是 pi 自己的升级命令，npm -g 对它永远是错位安装。

**处置**：

- 服务器：无需再修（升级已完成且自洽）。验证：`pi --version` = 1.0.4；`pi -p --no-session` 真实调用回 PONG（shim 与 `node cli.js` 直跑双确认）。
- **产品守卫**：`buildRemoteAlignCommand` 加前置拦截——`command -v pi` 落在 `*/pi-node/node-*/bin/*` 时输出 `pipi-align-blocked: …` 并 `exit 3`，绝不对托管树执行 npm -g。真机干跑验证：`PATH-PI=…/pi-node/…/bin/pi`、`OUTER-EXIT=3`。测试钉住（pi-version.test.ts 23 例，含「命令里不得出现 `pi update` 字面量」的 ADR 0009 守卫——提示文案也因此绕开了这个字面量）。

**教训**：

1. **对齐/安装前先问「pi 从哪来」**：`command -v pi` 的路径形态就是安装来源的指纹（pi-node 托管 / bun / 系统 npm）。只看「版本对不对」不看「装在哪」，就会把两个安装来源混写在一台机上。
2. **npm -g 永远不该指向托管树**：托管安装自带 npm，PATH 前置使「用户全局 npm」与「托管 npm」静默互换——任何假设 npm 目标位置的全局安装命令都要先验证 `command -v npm`。
3. **活进程 + 就地重写 dist = 惰性加载炸雷**：ESM 惰性 chunk 加载意味着「升级完了一切正常」是假象，已运行的会话随时可能在下一次动态 import 时撞中间态。修完要让用户重开会话。
4. 探针自身教训：非交互 exec 通道（a）不在登录 shell 里，PATH 与用户终端不同——`bash -lc`/`bash -ic` 才能复现用户路径；（b）stdin 不关会让 `-p` 模式可能挂到 EOF——加 `</dev/null`；（c）多层引号嵌套时把脚本走 stdin，别拼 argv。

## 分支窗口反复弹「界面渲染出错，已阻止白屏 / RangeError: Maximum call stack size exceeded」

**症状**：打开长会话的「会话分支」后整窗变成崩溃兜底页（`界面渲染出错，已阻止白屏` + `RangeError: Maximum call stack size exceeded`）；点「重试渲染」再开还是弹，重载窗口也只是把同一个弹窗再来一遍。

**Phase 1 loop**：`node scripts/diagnose-tree-crash.mjs --shape=chain --entries=20000`（`npm run diagnose:tree-crash`）。脚本自己 `npx electron .`（不用打包），CDP 里建 tab → 点「会话分支」→ 找 `.crash-screen`；三种 seed：`chain`（线性，= pi 的真实形状）、`bush`（同样条数但浅，用来砍掉「载荷太大」的假设）、`dup-ring`（重复 id + 不一致 parentId）。修复前 chain RED、dup-ring RED。

**取证**（全部可复现，不是推断）：

1. 本机 `%APPDATA%/pipi/pipi-debug.log` 里同一栈出现 6 次：`Array.values | walk (TreeDialog.tsx:492:23) | TreeDialog (:263:3) | div | ChatView2 (ChatPane.tsx:1190:66)`，全部发生在**远程会话 rpc-1**（`/home/crscu/.pi/agent/sessions/--data-liuchang-CRSCU…/2026-10-02T03-28-34-420Z_*.jsonl`，就是上面那台 `192.168.10.49`）的 `get_entries` 响应落地后 2-5s。该会话单次 `get_entries` 要 50-100s，主进程堆一度 1.3GB —— 巨型会话。
2. **二分深度而不是猜**：链式 seed 4000 层就 RED，3000 层 GREEN；同条数的 `bush`（2 万条全挂一个根，深度 2）20000 GREEN → 与条数/体积无关，**只与深度有关**。
3. 阈值 ≈ 3500-4000 层，而 pi 把**每个 entry 链上前一条**，所以深度 = 会话长度（本仓库自己的日志里就有 4532 / 4266 / 3488 条的会话；`tree-layout.ts` 的 `conversationLevel` 注释也早写过这件事）。渲染器在 React 渲染帧里起步，栈比 node 浅：同一函数在 node 里约 1 万层才炸。crash 处 `walk` 是 `TreeDialog` 里 `toolCalls` memo 的**递归** `children` 遍历。
4. 同族第二个缺陷（修完第一个才露出来）：
   - `buildTreeFromEntries` 号称 cycle-safe，但它的防环读的是每个 id **最后**一条 `parentId`，挂载用的却是**每一条** occurrence → 重复 id 且 parentId 不一致时它能返回带环的树（用 43 条的 seed 就能让 `walk` 无限递归，弹窗完全相同）。
   - 即使树不再有环，`TreeDialog` 里「选中行被过滤掉 → 往上找最近的可见祖先」的 `while (cur && !filtered.some(…)) cur = parentById.get(cur)` **没有任何上界**，而它走的是 entry 的原始 `parentId`：父链成环、且环上成员都被默认过滤器挡住时（标准视图会隐藏 `thinking_level_change` 等记账条目），它在 `useEffect` 里空转，**整个渲染进程冻死**——不弹窗、不报错、没有「重试渲染」可按。CDP `Debugger.pause` 读暂停帧的实时局部变量坐实了现场：`selectedId` = pi 刚 append 的一条 `thinking_level_change`（被过滤），`cur` = `dupX`，环 `dupX↔dupB`。

**根因**：会话树是「随会话长度变深」的结构，而渲染期对它的遍历是递归的；父链遍历也没有上界。不变量 #4（来自模型/网络/文件的渲染期数据 = 不受信）在这里被违反：深度、重复 id、parentId 环都是外部输入形状。

**处置**：

- `src/shared/tree-index.ts`（新）：`indexToolCalls(tree)` —— 显式栈迭代 + visited 守卫（重复节点只索引一次，环上终止）。`TreeDialog` 的 `toolCalls` memo 改为调用它，递归实现删除。
- `src/shared/tree-layout.ts`：`nearestVisibleAncestor(parentOf, startId, isVisible)` —— 有界父链上行（**每个 id 最多探一次**）。`TreeDialog` 的选中回退 effect 改调它，顺带把每步 O(行数) 的 `filtered.some` 换成一次构建的 Set。
- `src/shared/tree-build.ts`：重复 id 以**首个 occurrence 为准**（`nodeMap` / `parentOf` / 挂载三者同源），既有的 memoized 防环检查于是对它真正挂上去的那些边成立——重复 id 不再可能闭出环。
- 回归测试（都钉在纯函数 seam 上，node 里秒级）：`tree-index.test.ts`（2 万层链 + 重复节点环终止）、`tree-layout.test.ts` 的 `nearestVisibleAncestor`（环上每个 id 只探一次）、`tree-build.test.ts` 的「重复 id 不一致 parentId 不得成环」。
- 真机 loop：`scripts/diagnose-tree-crash.mjs`（`npm run diagnose:tree-crash`）。它不只看首屏：跑完会滚到底、折叠、搜索一遍再复查一次崩溃页，确认崩溃没有「搬家」（`flattenTree` / `foldedAwayIds` / 窗口数学跑在同一棵深树上）。

**验证**：修复前 chain（4000/5000/6000/7000/8000/9000/10000/12000/15000/20000）与 dup-ring RED；修复后 chain 20000、bush 20000、dup-ring ×3 全 GREEN，2 万行里 fold / search / scroll 正常（窗口只挂 35-55 行）。全量测试 1399 通过（新增 5），typecheck 通过。

**教训**：

1. **「会话多长，链就多深」是渲染层的一等约束**：任何在渲染期走 `children` 或 `parentId` 的遍历都必须迭代 + 有界，不能赌「会话不会那么长」。本仓库其它父链遍历（`ancestorIds` / `foldedAwayIds` / transcript builder）早就有守卫，唯独漏了这两处——漏一处就够白屏。
2. **防环检查必须用「真正挂上去的那条边」**：`buildTreeFromEntries` 里「nodeMap 取最后一条、挂载遍历每一条」的不一致，就是「文档写着 cycle-safe、实际能返回环」的根。三者同源之后，原有的检查才名副其实。
3. **弹窗不是最坏的失败**：无上界的 `while` 不报错也不弹窗，直接冻住渲染进程（CDP 的 `Runtime.evaluate` 再无回音）。这时 `Debugger.pause` 读暂停帧的局部变量，比读代码猜快一个数量级。
4. **先量形状再修**：`bush 20000 GREEN` 一条就把「载荷太大」砍掉，剩下只可能是深度；`Runtime.evaluate` 超时先于任何日志报错，说明「无声冻结」必须当成独立失败模式来测。
5. 探针自身：Electron 单实例 + 固定 `--user-data-dir` 会让被 kill 的上一次运行抢走 CDP（`Runtime.evaluate` 永不返回）。loop 现在用 `profile + pid` 且每次启动前杀干净，并把「CDP 无响应」显式当成一种失败打印出来。

**后续（同一症状的第二层）**：崩溃修掉之后，长会话打开分支仍然要整份读会话文件（实测 8.07MB / 2763 条，远程 60s、主进程堆 1.3GB）。处置见 `docs/adr/0011-session-entry-paging.md`：打开只读文件**最新一页**（400 条 / ≤1.5MB，实测 20-40ms）、更早的按需翻页、RPC 只吃增量。真机 loop 加了一段翻页探针（首屏落在最新一条、点按钮 +400、滚到顶再 +400、视口锚定不动、tail 载荷 ≤400 条）。

## 打开长会话「历史加载要一分钟」（2026-10-07，同一条远程会话）

日志（`pipi-debug.log`）把 55s 拆开了：`SPAWNED` → 4.0s pi 远端装载会话 → `get_state` 4.0s → **`[transcript] from-file OK messages=900 tail=120` 又 50.8s**。也就是说聊天历史这条路仍在**整份读 62MB**（SFTP）后 `slice(-120)`；同一个 tab 的会话树（ADR 0011）只要 1.45s。处置见 `docs/adr/0012-transcript-tail-window.md`：复用会话页引擎，只读最新一段（本机真实会话量到 18-20% 的字节），一致性由一次 `get_entries {since}` 探针承担。真实数据测试顺带抓到两个只在真文件上才暴露的问题：**窗口增长会把已读的字节重读一遍**（10MB 文件传输 37MB），以及**降级的页 `cursor: null` 被当成「到达文件头」**（于是 complete 判定错、计数校验必然失败、快路径永远失效）。
