## app 说「已同步」，其实一个字节都没落地：退出码被账本写入掩盖 (2026-10-01)

**症状（没有用户报过）**：免密 ssh 的远端（key-auth，`syncKeyAuthExtensions`）上，投递会「成功」——
`[skills] key-auth remote: wrote N`，`remoteKeyExtSyncHash` 被标记为已完成，本次连接不再重试。而远端
某些文件根本没变。更坏的是**第二次伤害**：下一次连接探测到「远端字节 ≠ 我们记的哈希」，而账本里这个
文件明明是我们的 → 分类只剩一种解释：「用户手改过」→ 从此**永久保留**，再也不升级。用户什么都没做，
却拿到了一个再也修不好的旧副本。

**这一条不是从故障现象追出来的，而是从「脚本不可能说出什么」推出来的**：应用脚本是一串 `sh` 命令，
它唯一的真值来源是退出码，而 shell 的退出码 = **最后一条命令**的退出码。最后一条是写账本。

**根因一：账本写入掩盖了中间任何一次写入失败。**

```sh
# 旧形状（每条写入一行）
echo <base64> | base64 -d > <目标>.pipi-tmp && mv -f <目标>.pipi-tmp <目标>
…
echo <账本>  | base64 -d > <.pipi.json>.pipi-tmp && mv -f … # 最后一行的退出码 = 整个脚本的退出码
```

中间任一次写入失败——磁盘满、权限、`.pipi-tmp` 位置上已经有个目录（EISDIR）——`&&` 让 rename 不跑
（这一半是对的：半截文件不会装上去），但脚本**继续往下走**，账本照写，退出 0 → `apply.ok` 为真 →
app 报已同步，而账本把一个**没有落地**的文件记成我们的。

**根因二（顺带查出来的独立缺陷）：读不出来的账本被当成「没有账本」。**

探测脚本原来写 `[ -f <账本> ]` + `base64 <账本> 2>/dev/null || true`。账本存在但读不出来（权限、
EISDIR、根本不是普通文件）时，输出里只有 `@@j` 没有任何 base64 → 解析成**空账本** → 我们发出去的每个
文件都被判成「用户的」→ 不再升级，而且下一条应用脚本会把这条假结论**写回远端当新账本**，销毁唯一
能分辨归属的证据。`|| true` 在这里不是「容错」，是「把失败翻译成谎言」。

**为什么这次能一次改对：先做一个受控实验，而不是先改代码。**

`set -e` 看起来是显而易见的修法，但它在**`A && B` 的左侧不生效**（状态正在被测试的命令被豁免），
所以「一行式 + `&&`」恰好是最需要它时不生效的写法。真 Linux（WSL）实测：

```
# 一行式：失败被豁免
$ sh -c 'set -e; echo x | base64 -d > /tmp/blocked.pipi-tmp && mv -f /tmp/blocked.pipi-tmp /tmp/blocked'; echo $?
0        # ← 目标位置是目录，写入失败，退出码却是 0

# 拆成两条语句：中止
$ sh -c 'set -e; echo x | base64 -d > /tmp/blocked.pipi-tmp; mv -f /tmp/blocked.pipi-tmp /tmp/blocked'; echo $?
1
```

（第二条那个 `1` 就是 `mv` 的失败，`set -e` 让它成为整个脚本的退出码。）

**处置（`src/main/content-sync.ts`）**：

1. 应用脚本第一行 `set -e`；写入拆成两条语句（`… > <目标>.pipi-tmp` 一行，`mv -f …` 一行）；账本仍在
   最后。于是任何一处失败都中止，远端保留**上一份账本**——什么都没忘，下次连接重试。
2. 探测用 `[ -e ]`（存在性，而不是「是不是普通文件」）；读失败打 `@@ju`；`parseProbe` 多返回
   `journalUnreadable`；`syncContentViaSsh` 看到就**拒绝同步**（一个应用往返都不发），错误里点名
   `.pipi.json` 和原因。这与本机路径一致：`ensureContent` 读账本抛错时整次 catch，什么都不写。
3. 退役的 `rm -f` **刻意不加 `|| true`**：失败要中止，因为中止保住账本条目、下次重试；吞掉错误则是
   「条目被丢弃但文件还在」——我们不再分发的扩展留在 pi 里继续被加载，且从此不可见。实测：`rm -f`
   一个非空目录 → 退出 1、账本未写、之前写好的文件仍在（下次因为字节等于目标而自愈）。

**验证**：

- 两条新写的红灯循环（先红后绿，真 Linux `wsl.exe` 扮 `ssh host sh -s`）：(A) 把 `.pipi-tmp` 位置上
  预先造成目录 → 期望 `ok:false`、无账本、目标不存在（改前是 `ok:true`）；(B) 先装一遍、改一个文件、
  把账本换成目录 → 期望 `ok:false`、错误点名 `.pipi.json`、用户改动原样、账本仍是个目录。
- 单元测试：脚本形状（`set -e` 在最前、账本在最后、写入是两条相邻语句、解码行内不得出现 `&&`）、
  probe 的 `-e` 与 `@@ju`、`syncContentViaSsh` 遇 `@@ju` 只发一个往返且拒绝、退役行不带 `|| true`。
- `npm run smoke:skills-wsl`（真 Linux）4 passed；全量 1141 passed | 4 skipped（1145）。

**顺带修掉的测试假件（这次改动一上来就有 10 个测试变红的原因）**：`skill-sync.test.ts` 的假远端
原样复演应用脚本，但它对**不认识的写入行静默忽略**——脚本形状一改，覆盖就断了而所有断言照样全绿。
现在遇到不认识的行直接返回失败。同类的两处（`extension-sync.test.ts` 只做形状断言、不复演）不受影响。

**教训**：

- **退出码是脚本唯一的真值来源**：任何「一串命令」的脚本，最后一条命令决定它说的是真是假；把账本写在
  最后，等于让账本的健康状况代表整次同步的健康状况。
- **`set -e` 不是全局开关**：`A && B` 左侧、`if` 条件、`||` 右侧都被豁免。「一行式 + `&&`」在语法上很
  漂亮，在语义上恰好绕开了这条保护。
- **`|| true` 会把「失败」翻译成「什么都没发生」**：只有在你确实希望「什么都没发生」时才写。读账本不是
  这种情况——读不到账本，和「没有账本」，是两个世界。
- **两处独立的缺陷可以共用一个症状**：写不进去（根因一）和读不出来（根因二）都表现成「同步过了但文件
  没变」，而且都会导致同一个永久冻结。只修原子性（`078522f` 的 `.pipi-tmp` + rename）解决的是「半截文件
  装上去」，没有解决「没落地却记成我们的」。
- **本机通道早就做对了这件事**：`ensureContent` 读不到账本就整次不写。ssh 通道缺的不是新知识，是与
  本地通道对齐——同一套语义的两个实现，差异只该在传输层。
- **每次「修失败上报」都要顺手检查假件是否会因此空转**：假件静默忽略未知行，等于把这次改动的覆盖
  悄悄抹掉，而红绿指示器还会告诉你一切正常。

**诚实的缺口**：这条通道上的失败只到 `console.error`（`src/main/index.ts` 的 `syncKeyAuthExtensions`），
渲染层不显示；tab 上那句提示文案属于当时别人未提交的工作流，没碰。记在 ADR 0005 的已知限制里。

## 同一批的同类项清扫：四种传输里的「读不到」（2026-10-01，下半天）

修完 shell 那一半，按「同类项」把同一个问题在别的传输上问了一遍：**谁把「读不出来」翻译成了「不存在」？**
答案不是只有远端脚本。`ContentIo.read` 的三家实现里，本机 fs 与 SFTP 都是 `catch { return null }` ——
`null` 在我们的规则里是「缺席」，而缺席是要被写入的。于是：读不出来的账本 → 空账本 → 我们发出的每个文件
都判成「用户的」；读不出来的文件 → 被我们写掉。

`src/main/content-sync.ts` 修法（接口契约写进注释，它就是契约）：

- `read` 三种返回：`null` = 不在、文本 = 内容、`UNREADABLE` = 在但读不出来；传输本身坏了（连接断了）照旧
  throw，调用方宁可拒绝也不猜。
- `nodeContentIo`：只有 `ENOENT`/`ENOTDIR` 算缺席（`ENOTDIR` 也确实是"这个路径上没有文件"）；`EISDIR`、
  `EACCES`、`EPERM`、`ELOOP` 一律 `UNREADABLE`（一个 `sudo pi` 跑出来的 root 文件、一个同名目录）。
- `sftpContentIo`：`get` 对「没有这个文件」和「不让我读」都 reject，所以失败之后再问一次 `exists`（真库
  走下去是 `lstat`）——顺利路径不加往返，只有失败路径多一次。
- `syncContent`：账本读到 `UNREADABLE` 直接抛，错误里点名 `.pipi.json`（与 ssh 的 `@@ju`、与本机
  `ensureContent` 同一个决定）。
- `ensureContent`：账本读不出来整次拒绝；**单个文件**读不出来改为保留并上报，不再让一个读不出的文件阻断
  整次升级（旧行为是外层 catch 吞掉，结果是"什么都没同步"而且只有一行日志）。
- `logDivergences` 现在收 `current`，对 `UNREADABLE` 的条目说「could not be read」，不再对没看见过的文件
  猜「edited by the user」。

**验证**：`content-sync.test.ts` 25 → 27 条（假 io 复演三种返回值；真 fs 验 `ENOENT`/`ENOTDIR` → `null`、
目录 → `UNREADABLE`；SFTP 假 client 断言 `exists` 只在 `get` 失败后被调用且调用序列完全确定；「一个读不
出的文件不阻断其它文件」并要求日志不出现「edited by the user」；「账本读不出来时一个字节都不写」）；全量
1148 passed | 4 skipped（1152）；`npm run smoke:skills-wsl` 真 Linux 4 passed；另跑一次真机数据——把
`~/.pi/agent/skills` 复制到临时目录后 `ensureContent` 仍是 `{"written":[],"diverged":[],"retired":[]}`，`~/.pi/agent/{extensions,agents}`
的副本上 `ensureShippedAgentHome` 仍是 `{"extensions":[],"agents":[],"diverged":[],"retired":[]}`。

**顺带发现的假件问题**：`extension-sync.test.ts` 的 SFTP 假 client 没有 `exists`，于是新代码一走失败路径
就 `client.exists is not a function`，11 个测试变红 —— 真库有这个方法，假件缺它，补上（`lstat` 语义：
在 → `"-"`，不在 → `false`）。这与上半天那个「假件静默忽略未知行」是同一类问题的两面：**假件比真库宽松，
覆盖就会悄悄消失；假件比真库严格，改动就会立刻现形**。后者可以接受。

**教训**：「读不到 ≠ 不存在」不是 shell 的问题，是**所有传输的共同语义**；把它写在接口注释里，比写在
某一次提交说明里活得久。
