# 技能不做云端热更新，也不做技能市场

技能只能随**签名过的 app 版本**一起更新。我们不从服务器下发技能文件、不做"技能商店"、不做让第三方发布技能再由我们分发的市场。

## 为什么放到界外

技能是**给模型看的指令文本**，它会在用户的机器上、以 pi 进程的权限、驱动 bash 与文件写入。一个能远程更新技能的通道，就是一个能远程执行代码的通道——而它的传输链路（我们的服务器、对象的完整性、用户被诱导安装的"热门技能"）都不在用户的信任边界内。pipi 的定位是"让 AI 在你远程服务器上跑"，这类用户的机器上往往有生产环境；用一条热更新通道在这个信任边界上开洞，与产品的卖点直接冲突。

顺带，市场带来的是我们要对第三方内容负责：审核、下架、侵权投诉、恶意技能的第一响应。这些成本与"整合层"的定位无关，且永远长不完。

## 已有的逃生阀

- **用户自己的技能永远优先**：`~/.pi/agent/skills/` 是用户的目录，我们只写自己发过、且没被改过的文件（见 ADR 0004 的所有权规则）。
- **装任何人的技能**：pi 原生支持从目录、包、settings（`skills` 数组）加载技能，用户想装谁的都行，不需要经过我们。
- **上游升级**：我们跟着上游走（`scripts/vendor-skills.mjs`），随 app 版本发布。用户想要的"新技能"通过 app 更新到手。
- **团队共享技能包**：付费方向是"把团队自己的技能包分发到成员的远程主机上"——**内容由团队自己提供**，我们只做投递，不做内容托管与审核。
- **用户自己的 pi 扩展包同理**：`pi update --all`（升级全局 pi + 用户扩展包）与 `pi update --extensions`（远程对齐时顺手升级）都不在 app 里——app 只装我们钉住的版本，用户的包由用户自己管（`docs/adr/0009-no-chase-latest.md`）。
